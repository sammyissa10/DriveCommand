# TKT-0085 — "route template doesn't show routes" → Route / Template / Trip convergence

**Status:** Deferred — needs a product decision, not a quick fix.
**Filed from:** `/carrier/loads/new` (New Load → "dispatch immediately" toggle), org Madia LLC.
**Investigated:** 2026-07-24 (during the 83/84/85/86 batch).

## Symptom

Owner turns on "dispatch immediately" while creating a load (or opens New Trip),
the **Route template** dropdown is empty, so there's nothing to pick. Reporter had
"created a route" and expected it to appear.

## Why it happens (verified against prod + code)

The dispatch route-template dropdown fetches `/api/v1/carrier/route-templates/active`,
which returns `route_templates WHERE org_id = ? AND active = true`
(`app/api/v1/carrier/route-templates/active/route.ts`). Consumers:
`components/carrier/loads/LoadForm.tsx:275`, `carrier/trips/new/NewTripMobile.tsx:94`.

The **only** UI that writes `route_templates` is `/carrier/templates` ("Route Templates"),
which is **not in the sidebar**. The sidebar "Routes" item points at `/routes`
(`components/Sidebar/index.tsx:287`), the *legacy* route builder, which writes the
`Route` table — a different system entirely. (The sidebar comment calling
`/carrier/templates` "Rate Sheets" is simply wrong.)

So a normal user has no reachable path to create a route template → the dropdown is
empty for every real org. Prod confirms:

| Org | `route_templates` | active | legacy `Route` |
|-----|------------------:|-------:|---------------:|
| Madia LLC (reporter) | 0 | 0 | 1 |
| DriveCommand Demo | 1 | 1 | 4 |

Madia's exact fingerprint: 1 legacy route they built, 0 templates the dropdown can read.
Not RLS, not a query bug — the table the dropdown reads is genuinely empty.

Aggravating: on fetch error `LoadForm.tsx:282` silently shows an empty dropdown
("non-critical"), so a real error would look identical to "no data." Here it's truly 0 rows.

## The deeper structural problem

`Route` and `RouteTemplate` are NOT the redundant pair. The schema shows they're
built for different jobs:

- **`Route` (schema.prisma:497)** — a single, scheduled, **assigned** journey:
  `driverId` required, `truckId`, `scheduledDate`, `status`, `completedAt`,
  `startOdometer`/`endOdometer`, `distanceMiles`; hangs loads/expenses/payments/
  safetyEvents. It gets *executed and completed*. 35 files consume it (driver portal
  "My Route", geofencing, mobile owner+driver routes, lane/route analytics).
- **`RouteTemplate` (schema.prisma:2152)** — a **recurring blueprint**: no `driverId`/
  `scheduledDate`; instead `defaultDriverId`, `scheduleType`, `recurrenceRule`,
  `recurrenceTimezone`, `autoGenerateDaysAhead`; required `clientId` + optional
  `contractId`; stop times are *offsets* (`apptWindowStartOffsetMin`) not absolute.
  `@@map` relation `dispatches Trip[]` — it's a factory that stamps out trips.

Analogy: a **RouteTemplate is a recurring calendar series**; each **Trip it generates
is one event**. A template is the mold, not a route.

The **real redundancy is `Route` (legacy) vs `Trip` (carrier)** — *both* are "one driver
+ truck + stops executed on a date." Trip is the carrier-portal instance (fed by
templates, has the stop timeline from TKT-0086); Route is the older owner-portal
instance. The intended spine is:

```
RouteTemplate (blueprint)  →  Trip (instance a driver runs)
Route (legacy)  ←  the odd one out: an older parallel "instance" never wired to templates
```

TKT-0085 is slippery because the reporter built a legacy **Route**, but dispatch only
speaks **Template → Trip**, and the two instance-worlds were never merged.

## Options considered

- **(rejected) Repoint sidebar "Routes" → `/carrier/templates`.** Strands the legacy
  `Route` system that 35 files (incl. the driver app) depend on. Also collides with the
  sidebar's MAX-5 operations-items constraint if merely *added*.
- **(band-aid) Empty-state hint in the dropdown** ("No route templates yet — create one →").
  Stops the silent dead-end but doesn't fix the orphaned-feature root cause.
- **(a) RECOMMENDED — make route templates creatable in context.** Add a
  "＋ New route template" affordance in the dispatch picker (New Trip / New Load) so the
  thing that feeds dispatch can be created where it's used. Keeps the two concepts cleanly
  separated (template = reusable blueprint; route = driver operational route). No data
  migration, no risk to the 35 legacy `Route` consumers.
- **(b) Make legacy Routes dispatchable.** Source the picker from `Route` and copy its
  `RouteStop`s into the trip (stop-stamping machinery already exists in `updateTrip` and
  `lib/carrier/dispatch-generator.ts:424`). Bigger; blurs two genuinely different concepts.
- **(milestone) Converge `Route` and `Trip`.** The correct long-term shape: make Trip the
  single operational instance, migrate the 35 `Route` consumers onto it, and let templates
  feed it. Real migration — its own milestone, not a ticket.

## Recommendation

Ship (a) as its own scoped GSD task (a small feature: create-template-in-context + wiring).
Separately, put "converge Route vs Trip" on the roadmap as a milestone-level decision — that
is the actual fix for the confusion, and it's too big to smuggle into a bug ticket.
