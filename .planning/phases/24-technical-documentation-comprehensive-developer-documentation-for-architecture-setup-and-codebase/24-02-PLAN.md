**docs/stack.md** — Technology stack reference.

Include these sections:

1. **Core Framework: Next.js 16 (App Router)**
   - Version: ^16.1.6
   - All pages are server components by default. Client components use `'use client'` directive.
   - Route groups: `(owner)`, `(driver)`, `(admin)` — parentheses mean the group name is not part of the URL.
   - API routes live under `src/app/api/`.
   - Server actions are defined in `actions/` subdirectories within each portal's route group.
   - Layouts: each portal has its own `layout.tsx` that wraps all pages in that group.

2. **ORM: Prisma 7.4**
   - Version: ^7.4.0 with `@prisma/adapter-pg` ^7.4.0
   - Uses the pg driver adapter (required for Prisma 7 with PostgreSQL connection pooling).
   - Client generated to `src/generated/prisma/` via `generator client { output = "../src/generated/prisma" }`.
   - Singleton client pattern in `src/lib/db/prisma.ts` to survive Vercel warm reuse.
   - Run `npx prisma generate` after any schema change.
   - Run `npx prisma db push` for local schema sync (replaces migrations in dev).

3. **Database: PostgreSQL via Supabase**
   - Hosted on Supabase (managed PostgreSQL with Row Level Security support).
   - Connection via `pg.Pool` with Supabase's Session Mode pooler (port 6543, not 5432).
   - RLS policies enforce tenant isolation at the database level.

4. **Styling: Tailwind CSS + shadcn/ui**
   - Tailwind CSS ^3.4.1 — utility-first CSS.
   - shadcn/ui — unstyled Radix UI primitives styled with Tailwind. Components live in `src/components/ui/`.
   - Radix UI packages used: dialog, alert-dialog, popover, select, separator, slot, switch, tabs, tooltip.
   - `class-variance-authority` (^0.7.1) for component variant patterns.
   - `tailwind-merge` (^3.4.1) + `clsx` (^2.1.1) for conditional class composition.
   - `lucide-react` (^0.564.0) for icons.

5. **Email: Nodemailer via Gmail SMTP**
   - `nodemailer` ^8.0.1 — SMTP transport.
   - `@react-email/components` + `@react-email/render` — write email templates as React components, render to HTML.

6. **Validation: Zod**

**docs/modules.md** — Feature modules reference.

Write a section for each module with: URL path, purpose (2-3 sentences), and key files.

1. **Trucks** — `/trucks`
   Purpose: Manage the fleet. Add trucks with VIN, make, model, year, odometer. Track documents (registration, insurance) with expiry alerts. View maintenance history and scheduled services per truck.
   Key files: `src/app/(owner)/trucks/`

2. **Drivers** — `/drivers`
   Purpose: Manage drivers within the tenant. Invite new drivers via email (creates a DriverInvitation, sends invite email). View driver profiles, assigned routes, documents, and safety scores.
   Key files: `src/app/(owner)/drivers/`, `src/lib/email/send-driver-invitation.ts`

3. **Routes** — `/routes`
   Purpose: Create and track trips. A Route connects a driver, a truck, an origin, and a destination with a scheduled date. Supports multi-stop routes (RouteStop model). Owners can track route status (PLANNED → IN_PROGRESS → COMPLETED) and attach expenses and payments.
   Key files: `src/app/(owner)/routes/`

4. **Loads / Dispatch** — `/loads`
   Purpose: Manage freight loads through the full dispatch lifecycle (PENDING → DISPATCHED → PICKED_UP → IN_TRANSIT → DELIVERED → INVOICED). Links loads to customers, drivers, trucks, and routes. Each load gets a unique `trackingToken` for the public shipment tracking page at `/track`.
   Key files: `src/app/(owner)/loads/`, `src/app/track/`

5. **Invoices** — `/invoices`
   Purpose: Create and manage invoices for customers. Invoices can be linked to a load/route. Supports line items, tax, due dates, and status tracking (DRAFT → SENT → PAID → OVERDUE). PDF generation for download and email.
   Key files: `src/app/(owner)/invoices/`

6. **Payroll** — `/payroll`
   Purpose: Track driver pay periods. Each PayrollRecord covers a period with base pay, bonuses, deductions, and miles logged. Status lifecycle: DRAFT → APPROVED → PAID. PDF payslip generation.
   Key files: `src/app/(owner)/payroll/`

7. **CRM** — `/crm`
   Purpose: Customer relationship management. Track shippers/brokers as Customers with contact info, load history, and revenue totals. Log interactions (calls, emails, meetings). Automated interactions are created when loads are updated or ETA notifications are sent.
   Key files: `src/app/(owner)/crm/`

8. **Compliance** — `/compliance`
   Purpose: Document expiry tracking. Shows upcoming expiry dates for truck documents (registration, insurance) and driver documents (licenses). Triggers email reminders via the daily cron job.
   Key files: `src/app/(owner)/compliance/`, `src/lib/email/send-document-expiry-reminder.ts`

9. **AI Documents** — `/ai-documents`
   Purpose: Upload and AI-read rate confirmations, invoices, and load tenders. Uses Claude claude-sonnet-4-6 to extract structured data (origin, destination, rate, dates) from PDF or image uploads. Extracted data can auto-populate load and route forms.
   Key files: `src/app/(owner)/ai-documents/`, `src/app/api/documents/`

10. **Profit Predictor** — `/profit-predictor`
    Purpose: AI-powered profitability analysis. Owner inputs a potential load (origin, destination, rate, weight) and gets an AI assessment of profitability based on historical fuel costs, lane performance, and the tenant's `profitMarginThreshold` setting.
    Key files: `src/app/(owner)/profit-predictor/`

11. **Lane Analytics** — `/lane-analytics`
    Purpose: Profitability analysis by route lane (origin–destination pair). Aggregates revenue, expenses, and margin per lane across all completed routes. Helps owners identify their most and least profitable lanes.
    Key files: `src/app/(owner)/lane-analytics/`

12. **Live Map** — `/live-map`
    Purpose: Real-time truck location map. Displays GPS pings from the GPSLocation table on a Leaflet map. Truck positions update on an interval. GPS data is submitted by the driver app or via the GPS API endpoint.
    Key files: `src/app/(owner)/live-map/`, `src/app/api/gps/`

13. **Fuel Dashboard** — `/fuel`
    Purpose: Fuel economy tracking. Log fill-ups (quantity, cost, odometer) per truck. Dashboard shows MPG trends, cost per mile, and total fuel spend. Supports estimated fuel records for routes without explicit fill-up data.
    Key files: `src/app/(owner)/fuel/`

14. **Safety Analytics** — `/safety`
    Purpose: Driver safety scoring. SafetyEvents (harsh braking, speeding, etc.) are logged per truck/driver/route. Dashboard shows event counts by type and severity, safety scores per driver, and trend charts.
    Key files: `src/app/(owner)/safety/`

15. **IFTA** — `/ifta`
    Purpose: International Fuel Tax Agreement reporting. Aggregates miles driven and fuel purchased per jurisdiction to help prepare quarterly IFTA filings.
    Key files: `src/app/(owner)/ifta/`

16. **Tags** — `/tags`
    Purpose: Color labels for organizing trucks and drivers. Tags are tenant-scoped. Can be applied to any truck or user for filtering and grouping in list views.
    Key files: `src/app/(owner)/tags/`

17. **Settings** — `/settings`
    Purpose: Tenant configuration. Set tenant name, timezone, and profit margin threshold. Manage integrations (QuickBooks, Samsara, KeepTruckin, factoring services, email providers).
    Key files: `src/app/(owner)/settings/`

18. **Support (Owner)** — `/support`
    Purpose: Owner submits support tickets to the DriveCommand team. Ticket has a title, description, category, and priority. Owners can message back and forth with admins through a TicketMessage thread.
    Key files: `src/app/(owner)/support/`

19. **Driver Portal** — `/my-route`, `/my-load`, `/my-tickets`, `/hours`, `/incidents`, `/messages`

**docs/setup.md** — Local development setup guide.

Write a complete, step-by-step guide. A developer should be able to follow this from zero to a running local app.

Sections:

1. **Prerequisites**
   - Node.js 20+
   - npm or pnpm
   - Git
   - A Supabase account (free tier sufficient) with a project created
   - A Gmail account with an App Password (for email features — optional to skip)

2. **Clone and Install**
   ```bash
   git clone <repo-url>
   cd drivecommand
   npm install
   ```

3. **Environment Variables**
   Copy the example file:
   ```bash
   cp .env.example .env.local
   ```

   Fill in each variable. Reference the table (pull values from .env.example, document each):

   | Variable | Required | Description | Where to get it |
   |---|---|---|---|
   | DATABASE_URL | Yes | PostgreSQL connection string | Supabase Dashboard → Settings → Database → Connection string (URI). Use port 6543 (Session Mode pooler) for Vercel; use port 5432 (direct) for local dev. |
   | AUTH_SECRET | Yes | 32+ char secret for session encryption | Run: `openssl rand -base64 32` |
   | NEXT_PUBLIC_APP_URL | Yes | App base URL | `http://localhost:3000` for local dev |
   | GMAIL_USER | Email | Gmail address for sending email | Your Gmail address |
   | GMAIL_APP_PASSWORD | Email | Google App Password | Google Account → Security → 2-Step Verification → App Passwords |
   | GMAIL_FROM_NAME | Email | Display name in sent emails | e.g. "DriveCommand" (optional) |
   | ANTHROPIC_API_KEY | AI features | Enables AI documents + profit predictor | https://console.anthropic.com/settings/keys |
   | S3_ENDPOINT | File upload | S3-compatible endpoint | Cloudflare R2: `https://<account>.r2.cloudflarestorage.com` |
   | S3_REGION | File upload | Region (R2 uses "auto") | `auto` for R2 |
   | S3_ACCESS_KEY_ID | File upload | S3 access key | R2: Cloudflare Dashboard → R2 → Manage R2 API Tokens |
   | S3_SECRET_ACCESS_KEY | File upload | S3 secret key | Same as above |
   | S3_BUCKET | File upload | Bucket name | Your R2 bucket name |
   | NEXT_PUBLIC_GOOGLE_MAPS_API_KEY | Address autocomplete | Google Maps API key | https://console.cloud.google.com → APIs & Services → Credentials |
   | ADMIN_SECRET_KEY | Yes | Password for sysadmin portal at /admin/login | Run: `openssl rand -base64 32` |
   | CRON_SECRET | Yes | Secret to protect /api/cron/* endpoints | Any random string for local; Vercel sets this automatically |
   | RESEND_API_KEY | (legacy) | Old Resend API key — not needed if using Gmail | Leave blank |

   Note: Variables without GMAIL_ or S3_ are required. Email and file storage variables are optional for initial local development.

   ```bash
   npx prisma db push
   ```

   ```bash
   npm run dev
   ```

**docs/deployment.md** — Vercel deployment guide.

Include these sections:

1. **Overview**
   DriveCommand deploys to Vercel. The deployment command is `npx vercel --prod`. Do NOT deploy via GitHub push — always use the CLI.

2. **Prerequisites**
   - Vercel account with the project linked
   - Vercel CLI installed: `npm i -g vercel`
   - All environment variables set in Vercel Dashboard → Settings → Environment Variables

3. **Environment Variables on Vercel**
   Set every variable from .env.example in the Vercel dashboard. Key differences from local:
   - `DATABASE_URL`: Use Supabase's **Session Mode pooler** (port **6543**), not port 5432. Example: `postgresql://postgres.[ref]:[pass]@aws-0-[region].pooler.supabase.com:6543/postgres`
   - `NEXT_PUBLIC_APP_URL`: Your production domain, e.g. `https://drivecommand.vercel.app`
   - `CRON_SECRET`: Vercel sets this automatically for Vercel Cron Jobs. You do not need to set it manually.

4. **Build Command**
   Defined in `vercel.json`:
   ```json
   {
     "buildCommand": "node scripts/migrate.mjs && prisma generate && next build"
   }
   ```
   This runs `scripts/migrate.mjs` to apply SQL migrations, then generates the Prisma client, then builds Next.js.

5. **Deploying**
   ```bash
   npx vercel --prod
   ```
   This deploys to the production URL. Always use `--prod` to target production (not a preview URL).

6. **Cron Jobs**
   Defined in `vercel.json`:

   | Path | Schedule | Purpose |
   |---|---|---|
   | `/api/cron/send-reminders` | Daily at 14:00 UTC | Send document expiry and maintenance reminder emails |
   | `/api/warmup` | Daily at 08:00 UTC | Keep the serverless function warm (reduces cold start latency) |
   | `/api/cron/auto-close-tickets` | Daily at 02:00 UTC | Auto-close resolved support tickets |

   Cron routes are protected by verifying the `Authorization: Bearer <CRON_SECRET>` header (Vercel injects this automatically).

7. **First Deployment Checklist**
   - [ ] All env vars set in Vercel dashboard
   - [ ] Supabase DATABASE_URL uses port 6543 (Session Mode pooler)
   - [ ] `ADMIN_SECRET_KEY` set (needed to log into sysadmin portal)
   - [ ] `AUTH_SECRET` is 32+ chars and matches between local and production
   - [ ] Gmail App Password configured (for email features)
   - [ ] R2/S3 bucket created and credentials set (for file uploads)
   - [ ] Run `npx vercel --prod` to deploy

**docs/email.md** — Email system guide.

Include these sections:

1. **Overview**
   DriveCommand sends transactional emails using Gmail SMTP via Nodemailer. Email templates are React components rendered to HTML using `@react-email/components` + `@react-email/render`. The active email client is in `src/lib/email/gmail-client.ts`.

2. **Gmail SMTP Setup**
   Required env vars:
   - `GMAIL_USER` — your Gmail address (e.g. `notifications@gmail.com`)
   - `GMAIL_APP_PASSWORD` — a 16-character Google App Password (NOT your Gmail login password)
   - `GMAIL_FROM_NAME` — optional display name (defaults to "DriveCommand")

   How to create a Google App Password:
   1. Enable 2-Step Verification on your Google account.
   2. Go to Google Account → Security → 2-Step Verification → App Passwords.
   3. Create a new app password for "Mail".
   4. Copy the 16-character code (spaces are stripped automatically by the client).

3. **How Sending Works** (based on src/lib/email/gmail-client.ts)
   - `getTransporter()` creates a lazy-initialized Nodemailer transporter singleton using `nodemailer.createTransport({ service: 'gmail', auth: { user, pass } })`.
   - `sendEmail({ to, subject, react })` renders the React email component to HTML, then calls `transporter.sendMail()`.
   - Returns `{ id }` (a nanoid) for compatibility with the previous Resend-based API.

4. **Email Templates**
   Templates are React components in `src/emails/` (or inline in the email sender files). They use `@react-email/components` primitives (Html, Head, Body, Container, Text, Link, Button, Hr).

5. **Email Trigger Points**
   Document every email sender function:

   | File | Trigger | Description |
   |---|---|---|
   | `send-driver-invitation.ts` | Owner invites a new driver | Sends invitation link to driver email |
   | `send-owner-invitation.ts` | SysAdmin invites a new owner | Sends invitation link to owner email |
   | `send-document-expiry-reminder.ts` | Daily cron (`/api/cron/send-reminders`) | Alerts owner when truck document expiry is approaching |
   | `send-driver-document-expiry-reminder.ts` | Daily cron (`/api/cron/send-reminders`) | Alerts owner when driver document expiry is approaching |
   | `send-maintenance-reminder.ts` | Daily cron (`/api/cron/send-reminders`) | Alerts owner when scheduled maintenance is due |
   | `send-geofence-alert.ts` | Load geofence trigger (GPS check) | Notifies customer when truck arrives at pickup or delivery |
   | `customer-notifications.ts` | Load status changes | Sends ETA and status update emails to customers |
   | `send-support-notifications.ts` | Support ticket activity | Notifies admin when new ticket created; notifies owner when admin replies |

6. **Notification Log (Idempotency)**
   Every email send is recorded in the `NotificationLog` table with a unique `idempotencyKey`. Before sending, the system checks if a log entry already exists for that key. If it does, the email is not sent again. This prevents duplicate emails from cron retries or double-submissions.

   Pattern:
   ```typescript
   // Check for existing log entry before sending:
   const existing = await prisma.notificationLog.findUnique({
     where: { idempotencyKey: key }
   });
   if (existing?.status === 'SENT') return; // skip duplicate
   ```

7. **Testing Email Locally**
   Set `GMAIL_USER` and `GMAIL_APP_PASSWORD` in `.env.local`. Emails will be sent from your Gmail account during local development. There is no sandbox mode — real emails are delivered. Use a test email address as the recipient during development.
