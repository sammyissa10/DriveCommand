**docs/architecture.md** — System design, portals, multi-tenancy, RLS, middleware.

Include these sections:

1. **System Overview**
   DriveCommand is a Next.js App Router application with three distinct user portals sharing a single PostgreSQL database. Each portal is implemented as a route group under `src/app/`:
   - `(owner)/` — Fleet owner and manager features
   - `(driver)/` — Driver-facing features
   - `(admin)/` — DriveCommand internal sysadmin tools

2. **Multi-Tenancy Design**
   - Every fleet operator is a Tenant (one row in the `Tenant` table). All data entities (trucks, routes, drivers, loads, etc.) carry a `tenantId UUID` foreign key.
   - Row Level Security (RLS) is enforced at the PostgreSQL level via Supabase RLS policies. Every tenant-scoped table has a policy that checks `current_setting('app.tenant_id') = tenantId`.
   - The `tenantId` is injected into each request via the `x-tenant-id` header by middleware, then picked up by API routes and server actions to call `set_config('app.tenant_id', tenantId, TRUE)` before any Prisma query.
   - **bypass_rls pattern**: Some operations (e.g., fetching the current user's own record, system admin checks) need to bypass RLS. These use `prisma.$executeRaw\`SELECT set_config('app.bypass_rls', 'on', TRUE)\`` as the first statement in a `prisma.$transaction`. The RLS policy checks `current_setting('app.bypass_rls', TRUE) = 'on'` and permits access if true.

3. **Middleware Flow** (describe the logic from src/middleware.ts)
   Explain the 5-step flow as a numbered list:
   1. Public paths (sign-in, sign-up, API auth routes, webhooks, /track) pass through without auth check.
   2. Requests without a valid `session` cookie are redirected to `/sign-in?redirect_url=<original>`.
   3. Authenticated users with no `tenantId` in the session are redirected to `/onboarding`.
   4. System admins (`isSystemAdmin=true`) are restricted to `/admin`, `/admin-support`, `/admin-dashboard`, `/tenants` paths — any other path redirects to `/admin-support`.
   5. DRIVER role users accessing OWNER_PATHS (e.g., `/dashboard`, `/trucks`) are redirected to `/my-route`.
   6. All authenticated tenant users get `x-tenant-id: <tenantId>` injected as a request header.

4. **Request Lifecycle** — describe how a typical owner portal page request flows:
   Browser → Middleware (validates session, injects x-tenant-id header) → Next.js Server Component (calls getSession() to read role/userId, calls server action or API route) → Server Action / API Route (reads x-tenant-id header, calls set_config to set tenant context, runs Prisma query through RLS-filtered PostgreSQL) → returns data to Server Component → renders to client.

5. **File Structure Overview**
   ```
   src/
     app/
       (owner)/       # Owner portal pages and server actions
       (driver)/      # Driver portal pages and server actions
       (admin)/       # SysAdmin portal pages
       api/           # API routes (auth, cron, GPS, documents, etc.)
     lib/
       auth/          # session.ts, server.ts, roles.ts
       db/            # prisma.ts (singleton Prisma client + pool)
       email/         # Gmail SMTP client, email sender functions
       notifications/ # Notification log utilities
       storage/       # S3/R2 file upload helpers
       finance/       # Revenue/expense calculation helpers
       safety/        # Safety event scoring
       geo/           # Geofencing utilities
   prisma/
     schema.prisma    # Single schema file, all models
   ```

6. **Key Design Decisions**
   - Next.js App Router server components used for data fetching (no client-side fetch for initial loads).
   - Prisma uses the `@prisma/adapter-pg` driver adapter with a singleton `pg.Pool` (max 5 connections) to survive Vercel's serverless warm reuse.
   - Session cookie is encrypted with AES-256-GCM using Web Crypto API (compatible with both Edge Runtime in middleware and Node.js in server components).
   - No third-party auth library — custom session management keeps the auth logic transparent and avoids Edge Runtime incompatibilities.

**docs/auth.md** — Session cookie auth, roles, guards, sysadmin.

Include these sections:

1. **Overview**
   DriveCommand uses a custom cookie-based session system (no NextAuth, no JWT library). The session is encrypted with AES-256-GCM using the Web Crypto API, stored as an httpOnly cookie named `session`, and expires after 7 days.

   Key files:
   - `src/lib/auth/session.ts` — encrypt/decrypt, getSession, setSession, clearSession
   - `src/lib/auth/server.ts` — requireAuth, requireRole, isSystemAdmin, getCurrentUser
   - `src/middleware.ts` — request-level auth guard and x-tenant-id injection

2. **SessionData shape**
   ```typescript
   interface SessionData {
     userId: string;      // UUID — User.id in database
     email: string;
     role: string;        // 'OWNER' | 'MANAGER' | 'DRIVER'
     tenantId: string;    // UUID — Tenant.id in database
     firstName?: string;
     lastName?: string;
     isSystemAdmin?: boolean;
   }
   ```

3. **Token Format**
   The cookie value is three base64url-encoded segments joined by `:`:
   `base64url(iv) : base64url(authTag) : base64url(ciphertext)`

   AES-256-GCM uses a 12-byte random IV and a 16-byte auth tag. The `AUTH_SECRET` env var is SHA-256 hashed to derive the 256-bit AES key.

4. **Session Functions**
   - `encrypt(payload: SessionData): Promise<string>` — encrypts and returns the token string
   - `decrypt(token: string | undefined): Promise<SessionData | null>` — decrypts; returns null on any failure (tampered token, wrong key, missing)
   - `getSession(): Promise<SessionData | null>` — reads and decrypts the `session` cookie from `next/headers`. Wrapped with `React.cache()` so decryption runs at most once per request.
   - `setSession(data: SessionData): Promise<void>` — encrypts and sets the cookie (httpOnly, secure in production, sameSite: lax, maxAge: 7 days)
   - `clearSession(): Promise<void>` — deletes the session cookie (logout)

5. **Auth Helpers (server.ts)**
   - `getRole()` — reads role from session cookie, no DB call. Use for role checks in server actions.
   - `requireAuth()` — throws if unauthenticated, returns userId. Use at the top of protected server actions.
   - `requireRole(allowedRoles)` — throws if role not in list. Use for role-gated actions.
   - `isSystemAdmin()` — runs a `$queryRaw` SELECT bypassing RLS to check `User.isSystemAdmin`. Use sparingly (DB call).
   - `getCurrentUser()` — fetches the User record using bypass_rls transaction. Use sparingly (DB call).

6. **Role Model**
   Three roles exist in the `UserRole` enum:
   - `OWNER` — full access to all owner portal features for their tenant
   - `MANAGER` — same as OWNER (not yet differentiated in middleware)
   - `DRIVER` — restricted to driver portal paths only

   Additionally, `User.isSystemAdmin: boolean` flags DriveCommand internal staff. System admins have a tenantId (they belong to a tenant) but are routed exclusively to admin portal paths.

7. **Login / Logout Flow**
   - Login: `POST /api/auth/login` — validates email + password with bcrypt against `User.passwordHash`, calls `setSession()` with user data, redirects to portal.
   - Logout: `POST /api/auth/logout` — calls `clearSession()`, redirects to `/sign-in`.
   - Accept invitation: `GET /accept-invitation?token=<id>` → `POST /api/auth/accept-invitation` — validates `DriverInvitation` by id and status, creates User record, calls `setSession()`.

8. **Server Action Pattern**
   ```typescript
   // Typical pattern at top of every protected server action:
   const userId = await requireAuth();
   const role = await requireRole([UserRole.OWNER, UserRole.MANAGER]);
   const session = await getSession();
   // session.tenantId is the tenant scope for this request
   ```

9. **isSystemAdmin Bypass**
   System admin users are checked via direct `$queryRaw` which bypasses RLS:
   ```typescript
   const rows = await prisma.$queryRaw\`
     SELECT "isSystemAdmin" FROM "User" WHERE id = ${session.userId}::uuid LIMIT 1
   \`;
   ```
   This is the only place where admin status is authoritatively checked — the `isSystemAdmin` field on the session cookie is supplementary and not used as the sole authority.

**docs/database.md** — Schema, Prisma client, RLS, bypass_rls, migrations.

Include these sections:

1. **Overview**
   PostgreSQL hosted on Supabase. Schema managed with Prisma. Generated client output: `src/generated/prisma/`. All tenant-scoped tables use Row Level Security (RLS) enforced in Supabase.

2. **Prisma Setup** (based on src/lib/db/prisma.ts)
   - Uses `@prisma/adapter-pg` driver adapter with a `pg.Pool` singleton (max: 5 connections).
   - Pool is stored on `globalThis` to survive Vercel's module-level warm reuse between serverless invocations.
   - DATABASE_URL must use Supabase's **Session Mode pooler** on port **6543** (not 5432 transaction mode — transaction mode drops connections after each tx, defeating pooling).

4. **Row Level Security (RLS)**
   All tenant-scoped tables have RLS enabled in Supabase. The pattern:
   - Supabase RLS policy checks `current_setting('app.tenant_id') = "tenantId"` on SELECT/INSERT/UPDATE/DELETE.
   - The `app.tenant_id` session variable is set at the start of each request via `prisma.$executeRaw\`SELECT set_config('app.tenant_id', ${tenantId}, TRUE)\``.
   - The `User` table has RLS too — queries against it need either `app.tenant_id` set or the `bypass_rls` pattern.

5. **bypass_rls Pattern**
   Some operations must read data without a tenant context filter (e.g., login — no session yet, sysadmin — spans tenants):

   ```typescript
   // In a Prisma transaction, set bypass_rls=on before the query:
   const [, user] = await prisma.$transaction([
     prisma.$executeRaw\`SELECT set_config('app.bypass_rls', 'on', TRUE)\`,
     prisma.user.findUnique({ where: { id: session.userId } }),
   ]);
   ```

   The RLS policy checks `current_setting('app.bypass_rls', TRUE) = 'on'` and permits the query if true. The `TRUE` parameter to `set_config` scopes it to the current transaction only.

   For `$queryRaw` (outside a transaction), RLS is bypassed entirely because `$queryRaw` runs as the database superuser.

6. **Migrations**
   Prisma migrations are NOT used in production. Instead, `scripts/migrate.mjs` is run as part of the Vercel build command (`node scripts/migrate.mjs && prisma generate && next build`). This script applies raw SQL migration files from a `migrations/` directory against the Supabase database directly.

   For local development, apply schema changes using:
   ```bash
   npx prisma db push
   ```

7. **Prisma Client Generation**
   The Prisma client is generated to `src/generated/prisma/` (not the default `node_modules`). This is required for Vercel deployment. After any schema change, run:
   ```bash
   npx prisma generate
   ```

   ```typescript
     prisma.$executeRaw\`SELECT set_config('app.tenant_id', ${tenantId}, TRUE)\`,
     prisma.truck.findMany({ where: { tenantId } }),
   ]);
   ```
