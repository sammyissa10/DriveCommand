## User Constraints (from CONTEXT.md)

### Locked Decisions

**Schema: RouteStop changes**
- Add `loadId String? @db.Uuid` — links each stop to the load it serves (nullable: fuel/weigh stops have no load)
- Add `contactName String?` — shipper/receiver contact at this stop
- Add `contactPhone String?`
- Add `bolNumber String?` — Bill of Lading number for this stop's load
- Add `poNumber String?` — Customer PO number

**Schema: Load changes**
- Add `pickupStopId String? @db.Uuid` — FK → RouteStop (set when load is assigned to a route)
- Add `deliveryStopId String? @db.Uuid` — FK → RouteStop
- Keep existing `pickupLat/pickupLng/deliveryLat/deliveryLng` — these remain as the geocoding cache on the load itself

**Geocoding trigger**
- Geocode origin → pickupLat/pickupLng and destination → deliveryLat/deliveryLng when a Load is created or when origin/destination changes
- Use Google Maps Geocoding API (already in the project for directions)
- Store as Decimal(10,8) / Decimal(11,8) — existing schema types

**RouteStop auto-creation**
- When `Load.routeId` is set (load assigned to a route), auto-create two RouteStops:
  - PICKUP stop: address=load.origin, lat=load.pickupLat, lng=load.pickupLng, position=auto, loadId=load.id
  - DELIVERY stop: address=load.destination, lat=load.deliveryLat, lng=load.deliveryLng, position=auto, loadId=load.id
- Then set `load.pickupStopId` and `load.deliveryStopId` back to the created stop IDs
- If a load is removed from a route, delete its associated RouteStops and null out pickupStopId/deliveryStopId

**Stop sequencing for multi-load routes**
- Default sequence: all PICKUP stops first (ordered by pickupDate), then all DELIVERY stops (ordered by deliveryDate)
- Position is 1-based integer on RouteStop
- Sequencing runs when a load is added/removed from a route or when stops are reordered

**Driver map behavior**
- Map reads `route.stops` ordered by `position` — polyline through all lat/lng coordinates
- Each stop marker shows: address, stop type (PICKUP/DELIVERY), associated load number + BOL number when tapped
- Auto-advance to next stop after driver departs current one (existing geofence logic)
- Stops with null lat/lng are shown in the timeline but skipped in the polyline (graceful degradation)

**Backfill for existing routes**
- Existing routes with loads but no RouteStops: run a one-time backfill migration
- For each load with routeId set and pickupLat/deliveryLat available, create RouteStops
- Loads missing coordinates: geocode them as part of the backfill
- Loads with no routeId: leave as-is (no route = no stops to create)

## Summary

The driver map is broken because RouteStops are never written to the database. The `map.tsx` screen fetches the active load via `driverApi.getLoad()`, which calls `/api/mobile/driver/loads/[id]`. That endpoint returns `stops` flattened from `route.stops`, but since no RouteStops exist for any route, `stops` is always `[]`. The `useDriverDirections` hook requires at least 2 stops with lat/lng to compute a polyline — so zero stops means no polyline, no markers.

The fix requires three coordinated pieces: (1) Prisma schema migration adding `loadId/contactName/contactPhone/bolNumber/poNumber` to RouteStop and `pickupStopId/deliveryStopId` to Load; (2) a geocoding utility that runs server-side when a load is created or updated, populating `pickupLat/pickupLng/deliveryLat/deliveryLng`; and (3) a RouteStop auto-creation hook that fires whenever `Load.routeId` is set, creating PICKUP and DELIVERY stops and writing back `pickupStopId/deliveryStopId`. A one-time backfill migration handles existing routes.

The CONTEXT.md states "Use Google Maps Geocoding API (already in the project for directions)." **This is incorrect for the geocoding layer.** The project does NOT use Google Maps Geocoding. It uses **Nominatim (OpenStreetMap)** for all geocoding — this is confirmed in `autocomplete/route.ts` and in `geofence-check.ts`, which already contains a reusable `geocodeAddress(address)` function using Nominatim. The directions layer does use OSRM (not Google Maps either). The planner should treat the geocoding API as Nominatim and extract the existing `geocodeAddress` function into a shared lib rather than introducing a new external API.

**Primary recommendation:** Extract the existing `geocodeAddress` function from `geofence-check.ts` into `apps/web/src/lib/geo/geocode.ts`, call it in the load create/update paths, and wire RouteStop auto-creation into the same transaction as the load mutation.

### Pattern 1: Geocoding at Load Save (Server-Side)

**What:** When a load is created or updated and origin/destination are present, call `geocodeAddress()` before writing to DB. Store result as `pickupLat/pickupLng` and `deliveryLat/deliveryLng`.

**When to use:** In every path that creates or updates a load's origin/destination:
- `apps/web/src/app/(owner)/actions/loads.ts` → `createLoad()` and `updateLoad()`
- `apps/web/src/app/api/mobile/owner/loads/route.ts` → `POST` handler
- `apps/web/src/app/api/mobile/owner/loads/[id]/route.ts` → `PATCH` handler (only when origin/destination fields are present in body)

**Example (extracted from existing pattern in geofence-check.ts):**
```typescript
// Source: apps/web/src/lib/geofencing/geofence-check.ts (lines 34-49) — adapt to shared lib
// apps/web/src/lib/geo/geocode.ts

/**
 * Forward-geocode an address string using Nominatim (OpenStreetMap).
 * Returns { lat, lng } or null on failure.
 * Never throws.
 */
export async function geocodeAddress(
  address: string
): Promise<{ lat: number; lng: number } | null> {
  try {
    const encoded = encodeURIComponent(address);
    const url = `https://nominatim.openstreetmap.org/search?q=${encoded}&format=json&limit=1`;
    const res = await fetch(url, {
      headers: { 'User-Agent': 'DriveCommand/1.0 fleet-management' },
      signal: AbortSignal.timeout(5000),
    });
    if (!res.ok) return null;
    const data = await res.json();
    if (!data.length) return null;
    return { lat: parseFloat(data[0].lat), lng: parseFloat(data[0].lon) };
  } catch {
    return null;
  }
}
```

**Error handling (Claude's discretion recommendation):** Save the load even if geocoding fails. Null lat/lng is gracefully handled everywhere in the codebase — `map.tsx` skips null-coord stops in the polyline, `useDriverDirections` filters them out. This is the existing pattern and is correct.

### Pattern 2: RouteStop Auto-Create/Delete in Transaction

**What:** When a load's `routeId` is set (assigned to a route), atomically create two RouteStops (PICKUP, DELIVERY) and write back `pickupStopId`/`deliveryStopId`. When `routeId` is cleared, delete those stops.

**When to use:** Must run inside the same `$transaction` as the load update to prevent orphaned stops.

**Sequencing (Claude's discretion recommendation):** Use full resequence on every add/remove. Fetch all stops for the route ordered by existing position, then reassign 1-based positions using the rule: PICKUP stops first (ordered by load.pickupDate), then DELIVERY stops (ordered by load.deliveryDate). Full resequence ensures no gaps.

```typescript
// Source: pattern derived from existing TX_OPTIONS usage throughout codebase
// apps/web/src/lib/route-stops/sync-route-stops.ts

import { Prisma } from '@/generated/prisma';
import type { PrismaTransactionClient } from '@/lib/db/prisma'; // use Prisma.TransactionClient

/**
 * Create RouteStops for a load being assigned to a route.
 * Returns { pickupStopId, deliveryStopId }.
 * Must be called inside an existing $transaction.
 */
export async function createRouteStopsForLoad(
  tx: Prisma.TransactionClient,
  params: {
    routeId: string;
    tenantId: string;
    load: {
      id: string;
      origin: string;
      destination: string;
      pickupLat: Prisma.Decimal | null;
      pickupLng: Prisma.Decimal | null;
      deliveryLat: Prisma.Decimal | null;
      deliveryLng: Prisma.Decimal | null;
    };
  }
): Promise<{ pickupStopId: string; deliveryStopId: string }> {
  const { routeId, tenantId, load } = params;

  // Get current max position for this route
  const maxPos = await tx.routeStop.aggregate({
    where: { routeId },
    _max: { position: true },
  });
  const basePos = (maxPos._max.position ?? 0) + 1;

  const [pickup, delivery] = await Promise.all([
    tx.routeStop.create({
      data: {
        routeId,
        tenantId,
        loadId: load.id,
        type: 'PICKUP',
        address: load.origin,
        lat: load.pickupLat,
        lng: load.pickupLng,
        position: basePos,
        status: 'PENDING',
      },
    }),
    tx.routeStop.create({
      data: {
        routeId,
        tenantId,
        loadId: load.id,
        type: 'DELIVERY',
        address: load.destination,
        lat: load.deliveryLat,
        lng: load.deliveryLng,
        position: basePos + 1,
        status: 'PENDING',
      },
    }),
  ]);

  // Full resequence after insertion
  await resequenceRouteStops(tx, routeId);

  return { pickupStopId: pickup.id, deliveryStopId: delivery.id };
}

/**
 * Delete RouteStops for a load being removed from a route.
 * Must be called inside an existing $transaction.
 */
export async function deleteRouteStopsForLoad(
  tx: Prisma.TransactionClient,
  params: { routeId: string; loadId: string }
): Promise<void> {
  await tx.routeStop.deleteMany({
    where: { routeId: params.routeId, loadId: params.loadId },
  });
  await resequenceRouteStops(tx, params.routeId);
}

/**
 * Full resequence: PICKUP stops first (by pickupDate), then DELIVERY stops (by deliveryDate).
 * Assigns 1-based positions.
 * Must be called inside an existing $transaction.
 */
async function resequenceRouteStops(
  tx: Prisma.TransactionClient,
  routeId: string
): Promise<void> {
  const stops = await tx.routeStop.findMany({
    where: { routeId },
    include: {
      // Need load dates for sorting — use loadId to join
    },
    orderBy: { position: 'asc' },
  });

  // Sort: PICKUP first, then DELIVERY; within each group order by existing position
  const pickups = stops.filter(s => s.type === 'PICKUP');
  const deliveries = stops.filter(s => s.type === 'DELIVERY');
  const ordered = [...pickups, ...deliveries];

  await Promise.all(
    ordered.map((stop, idx) =>
      tx.routeStop.update({
        where: { id: stop.id },
        data: { position: idx + 1 },
      })
    )
  );
}
```

### Pattern 3: Backfill Migration

**What:** A one-time Prisma migration SQL file that creates RouteStops for all existing loads that have `routeId` set and lat/lng populated.

**When to use:** Part of the schema migration. Run once, idempotent via `WHERE NOT EXISTS` guard.

**Important:** The backfill in the migration SQL should NOT call Nominatim (can't make HTTP calls in SQL). For loads with missing lat/lng, a separate Node.js backfill script should be run manually, or the missing-coord loads can be left for the next edit to geocode. The SQL-level backfill handles only loads that already have lat/lng.

```sql
-- Part of the new migration SQL
-- Backfill RouteStops for existing loads with routeId set and coordinates populated

INSERT INTO "RouteStop" ("id", "routeId", "tenantId", "loadId", "type", "address", "lat", "lng", "position", "status", "geofenceHit", "createdAt", "updatedAt")
SELECT
  gen_random_uuid(),
  l."routeId",
  l."tenantId",
  l."id",
  'PICKUP'::"RouteStopType",
  l."origin",
  l."pickupLat",
  l."pickupLng",
  ROW_NUMBER() OVER (PARTITION BY l."routeId" ORDER BY l."pickupDate" ASC) * 2 - 1,
  'PENDING'::"RouteStopStatus",
  false,
  NOW(),
  NOW()
FROM "Load" l
WHERE l."routeId" IS NOT NULL
  AND l."pickupLat" IS NOT NULL
  AND l."archivedAt" IS NULL
  AND NOT EXISTS (
    SELECT 1 FROM "RouteStop" rs
    WHERE rs."loadId" = l."id" AND rs."type" = 'PICKUP'
  );

INSERT INTO "RouteStop" ("id", "routeId", "tenantId", "loadId", "type", "address", "lat", "lng", "position", "status", "geofenceHit", "createdAt", "updatedAt")
SELECT
  gen_random_uuid(),
  l."routeId",
  l."tenantId",
  l."id",
  'DELIVERY'::"RouteStopType",
  l."destination",
  l."deliveryLat",
  l."deliveryLng",
  ROW_NUMBER() OVER (PARTITION BY l."routeId" ORDER BY l."deliveryDate" ASC) * 2,
  'PENDING'::"RouteStopStatus",
  false,
  NOW(),
  NOW()
FROM "Load" l
WHERE l."routeId" IS NOT NULL
  AND l."deliveryLat" IS NOT NULL
  AND l."archivedAt" IS NULL
  AND NOT EXISTS (
    SELECT 1 FROM "RouteStop" rs
    WHERE rs."loadId" = l."id" AND rs."type" = 'DELIVERY'
  );
```

**Note on backfill position sequencing:** The SQL backfill assigns approximate positions using window functions. After the backfill, positions should be re-normalized with a second pass or left as-is (they'll be correct relative to each other per route). A cleaner approach: insert with position=0 and run a resequence step.

### Pattern 4: Map Screen Needs No Changes (if stops data is correct)

**What:** The existing `map.tsx` already handles stops correctly — it filters null-coord stops from the polyline, displays numbered markers, and shows the next unvisited stop in the info panel. The `useDriverDirections` hook also already filters null-coord stops.

**When to use:** Once RouteStops are written with lat/lng, the map will work automatically. The only map changes needed are: (a) add `loadNumber` and `bolNumber` to the stop tap popup (currently just shows `address` and `position`), and (b) confirm the stop `type` field is included in the API response.

**Verification:** The driver loads `[id]` API currently returns `stop.lat`, `stop.lng`, `stop.position`, `stop.address`, `stop.status` via the RouteStop model. After schema migration, it will also return `stop.loadId`, `stop.bolNumber`, etc. No structural change needed to the API response — Prisma `include` returns all columns.

### Anti-Patterns to Avoid

- **Creating RouteStops outside a transaction:** If geocoding succeeds but the stop creation fails, or vice versa, you get inconsistent state. Always wrap geocoding + stop create in the same `$transaction`.
- **Calling Nominatim from within Prisma `$transaction`:** Network calls inside a DB transaction hold the connection open. Geocode BEFORE opening the transaction, then pass coords in.
- **Duplicating the geocodeAddress function:** It exists in `geofence-check.ts`. Extract it to `lib/geo/geocode.ts` and import from there. The geofence-check module should also be updated to import from the shared location.
- **Blocking load save on geocoding failure:** Geocoding can fail (Nominatim timeout, bad address). Always save the load with null coords rather than erroring. The map degrades gracefully with null coords.
- **Using position=0 in production:** The position column is 1-based throughout (schema comment, existing code). Start at 1.

## Common Pitfalls

### Pitfall 1: Circular FK Reference (Load ↔ RouteStop)
**What goes wrong:** `Load.pickupStopId` → `RouteStop.id`, and `RouteStop.loadId` → `Load.id`. This is a circular dependency. Prisma will reject the schema migration if both FKs are defined with non-nullable or if cycle detection fails.

**Why it happens:** Both tables reference each other. Prisma and PostgreSQL handle this with nullable FKs and deferred constraint evaluation, but the migration order matters.

**How to avoid:** Define both FKs as nullable (which the CONTEXT.md already specifies: `String? @db.Uuid`). In Prisma schema, use `@relation(name: "LoadPickupStop", fields: [...], references: [...])` with explicit relation names to disambiguate. In the migration SQL, use `ALTER TABLE ... ADD CONSTRAINT ... DEFERRABLE INITIALLY DEFERRED` if needed, or simply insert RouteStops first (since LoadId on RouteStop is nullable), then update Load with the stop IDs.

**Warning signs:** Prisma `migrate dev` fails with "Circular reference" or FK constraint violation during backfill.

### Pitfall 2: Nominatim Rate Limiting
**What goes wrong:** The Nominatim usage policy requires a maximum of 1 request per second. If the backfill migration or a bulk operation fires multiple geocoding requests simultaneously, it will get 429 errors or get the server IP blocked.

**Why it happens:** Nominatim is a free public service with strict rate limits.

**How to avoid:** For single load-save operations (one origin + one destination = 2 requests), this is not an issue. For the backfill, the SQL backfill only handles loads that ALREADY have lat/lng — no Nominatim calls needed. Loads without lat/lng need a separate Node.js script with `await sleep(1100)` between requests.

**Warning signs:** Geocoding returns null for valid addresses; 429 responses in server logs.

### Pitfall 3: Prisma Relation Name Collision
**What goes wrong:** Load already has a relation to RouteStop via `pickupStop` and `deliveryStop` FKs. Prisma requires explicit `@relation(name: "...")` annotations when a model has multiple relations to the same target model, or when there are circular references.

**Why it happens:** Prisma infers relation names automatically when there's only one relation between two models. With two FKs (pickupStopId, deliveryStopId) pointing to the same RouteStop model, explicit names are mandatory.

**How to avoid:** In schema.prisma, define:
```prisma
// On Load model:
pickupStop  RouteStop? @relation(name: "LoadPickupStop",   fields: [pickupStopId],   references: [id])
deliveryStop RouteStop? @relation(name: "LoadDeliveryStop", fields: [deliveryStopId], references: [id])

// On RouteStop model — must add back-references:
pickupForLoads  Load[] @relation(name: "LoadPickupStop")
deliveryForLoads Load[] @relation(name: "LoadDeliveryStop")
```

**Warning signs:** `prisma generate` fails with "Ambiguous relation" or "Missing @relation" error.

### Pitfall 4: Map Uses Load Stops, Not Route Stops Directly
**What goes wrong:** `map.tsx` fetches the active LOAD (`driverApi.getLoad()`), not the active ROUTE. The stops it uses come from `load.route.stops` — flattened in the API. If a load has no `routeId`, stops will always be `[]` regardless of whether RouteStops exist for other loads on the route.

**Why it happens:** The map screen was built around the load-centric view (one active load). The route-centric view is used elsewhere (owner portal). The two views share the same RouteStop data but via different traversal paths.

**How to avoid:** After RouteStops are created and `load.routeId` is set, the existing load detail API (`/api/mobile/driver/loads/[id]`) will return populated stops. No changes needed to `map.tsx` for the polyline/markers to work. However, the map currently calls `driverApi.getLoad(activeLoad?.id)` where `activeLoad` comes from the dashboard. The dashboard response must include `activeLoad.id` which it already does.

**Warning signs:** Map still shows empty stops after migration. Check: (1) does the load have `routeId` set? (2) do RouteStops exist for that route? (3) does the API response include `stops` with lat/lng?

### Pitfall 5: Web App Geocoding Path Is Different From Mobile
**What goes wrong:** The web `createLoad` server action (`loads.ts`) already accepts `pickupLat/pickupLng` as hidden form fields populated by the `AddressAutocomplete` component. This means the web path already geocodes via the UI — lat/lng arrive with the form submission. The mobile path (POST `/api/mobile/owner/loads`) does NOT have this — it receives only `origin` and `destination` strings.

**Why it happens:** The web form uses `AddressAutocomplete` which calls Nominatim and stores coords in hidden inputs. Mobile submits plain text addresses.

**How to avoid:** The geocoding-on-save logic is needed ONLY in the mobile API path, NOT in the web server action (which already has coords from the form). Add a server-side geocoding step only to:
- `POST /api/mobile/owner/loads` (new load via mobile, no coords provided)
- `PATCH /api/mobile/owner/loads/[id]` (load update via mobile, when origin/dest changed)

Do NOT modify `apps/web/src/app/(owner)/actions/loads.ts` to add server-side geocoding — it would double-geocode and the form-supplied coords are more precise (user selected from autocomplete).

### Pitfall 6: RouteStop `DEPARTED` Status vs Map Advancement
**What goes wrong:** The map uses `stop.status === 'DEPARTED'` to determine the "next unvisited" stop. The `DEPARTED` status is currently set by the geofence check logic. If a load's RouteStops are newly created (status=PENDING), the map will correctly show the first stop as "next." But if the backfill creates stops for a load that is already mid-route (status=IN_TRANSIT or PICKED_UP), those stops should ideally reflect current state.

**Why it happens:** Backfilled RouteStops are created with `status=PENDING` even if the associated load is past that stop.

**How to avoid:** For the backfill scope, creating all stops as `PENDING` is acceptable. The map will show stop #1 as next, which may not be accurate for in-progress loads. This is a known limitation documented for the backfill. Active route tracking accuracy improves for new loads going forward.

## Open Questions

1. **Circular FK: does Prisma handle Load ↔ RouteStop circular FK in migrate dev?**
   - What we know: Prisma supports circular relations via nullable FKs and explicit `@relation(name: ...)` annotations. PostgreSQL supports circular FKs with `DEFERRABLE INITIALLY DEFERRED`.
   - What's unclear: Whether `prisma migrate dev` will generate the correct SQL order automatically, or if a custom migration file is needed with deferred constraints.
   - Recommendation: Run `prisma migrate dev --create-only` first to inspect the generated SQL, then review before applying. May need `ADD CONSTRAINT ... DEFERRABLE INITIALLY DEFERRED` manually.

2. **Where to trigger RouteStop sync when routeId is set via the web actions?**
   - What we know: `createLoad` and `updateLoad` in `loads.ts` can set `routeId`. Currently no RouteStop creation happens there.
   - What's unclear: Should the web action path also create RouteStops, or only the mobile path?
   - Recommendation: Yes — both web and mobile load-save paths should sync RouteStops. The shared `syncRouteStopsForLoad()` function in `lib/route-stops/sync-route-stops.ts` should be called from both. This ensures web-created loads also get stops.

3. **Backfill for loads with routeId set but no lat/lng — scope decision**
   - What we know: The SQL backfill (using `WHERE pickupLat IS NOT NULL`) skips these loads. The CONTEXT.md says "geocode them as part of the backfill."
   - What's unclear: How many such loads exist? If it's a small number, a manual Node.js script is fine. If it's many, this needs a more robust approach.
   - Recommendation: Add a separate Node.js script (`scripts/backfill-geocode-missing-loads.ts`) that queries `WHERE routeId IS NOT NULL AND pickupLat IS NULL`, geocodes each with 1.1s delay, and updates. This is run manually once after migration, outside of SQL.
