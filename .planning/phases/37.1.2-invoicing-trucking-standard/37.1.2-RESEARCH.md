## Summary

Phase 37.1.2 is a schema + UI enhancement phase. The work spans three layers: (1) a Prisma migration to add two new PostgreSQL enums and nullable columns to existing tables, (2) validation schema updates in the `packages/validation` monorepo package, and (3) UI changes to `InvoiceItemsEditor` and `InvoiceForm` React components to support trucking-specific line item entry with FSC auto-calculation logic.

The existing codebase is well-structured for this addition. The `Invoice` model lives in `apps/web/prisma/schema.prisma`, the Zod validation schema in `packages/validation/src/invoice.ts`, server actions in `apps/web/src/app/(owner)/actions/invoices.ts`, and UI in `apps/web/src/components/invoices/`. The migration pattern is established — new enums use `DO $$ BEGIN / EXCEPTION WHEN duplicate_object` guards; new columns use `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` with defaults. The project uses Prisma 7.4 + Zod 4.3 + Next.js 16.

The `InvoiceItemsEditor` is a fully client-side `'use client'` component that serializes items to a JSON hidden field on form submission. This is the right place to add `itemType`/`unitType` dropdowns and FSC auto-calculation. No Radix Collapsible primitive is installed, so the "Freight Details" collapsible section must use a native `<details>`/`<summary>` element or a simple `useState` toggle — both work cleanly in Tailwind.

**Primary recommendation:** Write the migration first (enums + ALTER TABLE), regenerate the Prisma client, then update validation + actions + UI components in sequence.

### Pattern 1: Prisma Enum Addition Migration (PostgreSQL)
**What:** Add new PostgreSQL enum types using `DO $$ BEGIN ... EXCEPTION WHEN duplicate_object` guard, then add columns referencing them.
**When to use:** Any time a new Prisma enum needs to be added to an existing table.
**Example (from project's own migrations):**
```sql
-- Source: apps/web/prisma/migrations/20260327000005_add_driver_hos_and_incident/migration.sql
DO $$ BEGIN
  CREATE TYPE "InvoiceItemType" AS ENUM (
    'LINEHAUL', 'FUEL_SURCHARGE', 'DETENTION', 'STOP_OFF',
    'LAYOVER', 'TONU', 'LUMPER', 'ACCESSORIAL', 'TAX', 'OTHER'
  );
EXCEPTION WHEN duplicate_object THEN NULL;
END $$;

DO $$ BEGIN
  CREATE TYPE "InvoiceItemUnit" AS ENUM (
    'FLAT', 'PER_MILE', 'PER_CWT', 'PER_PIECE', 'PER_HOUR', 'PERCENT'
  );
EXCEPTION WHEN duplicate_object THEN NULL;
END $$;

-- Add enum columns to InvoiceItem with defaults (backward compatible)
ALTER TABLE "InvoiceItem"
  ADD COLUMN IF NOT EXISTS "itemType" "InvoiceItemType" NOT NULL DEFAULT 'OTHER',
  ADD COLUMN IF NOT EXISTS "unitType" "InvoiceItemUnit" NOT NULL DEFAULT 'FLAT';

-- Add nullable freight fields to Invoice
ALTER TABLE "Invoice"
  ADD COLUMN IF NOT EXISTS "bolNumber"   TEXT,
  ADD COLUMN IF NOT EXISTS "proNumber"   TEXT,
  ADD COLUMN IF NOT EXISTS "poNumber"    TEXT,
  ADD COLUMN IF NOT EXISTS "commodity"   TEXT,
  ADD COLUMN IF NOT EXISTS "weightLbs"   INTEGER,
  ADD COLUMN IF NOT EXISTS "pieces"      INTEGER,
  ADD COLUMN IF NOT EXISTS "loadedMiles" DECIMAL(10, 2);
```

### Pattern 5: FSC Amount Calculation (PERCENT unit type)
**What:** `amount = (quantity / 100) * unitPrice` for PERCENT unit type.
**When:** `unitType === 'PERCENT'` — quantity is the percentage value, unitPrice is the base amount being percentaged.
**Standard FSC behavior:**
- When adding a FUEL_SURCHARGE item, auto-populate `unitPrice` with the sum of all LINEHAUL item amounts on the invoice.
- `quantity` = the FSC percentage (e.g., 12 for 12%)
- `amount = (12 / 100) * linehaulTotal`
- User can override any field.

**The `getItemAmount` function in `InvoiceItemsEditor` must branch on `unitType`:**
```typescript
function getItemAmount(item: InvoiceItem): number {
  const qty = parseFloat(item.quantity) || 0;
  const price = parseFloat(item.unitPrice) || 0;
  if (item.unitType === 'PERCENT') {
    return (qty / 100) * price;
  }
  return qty * price;
}
```

### Anti-Patterns to Avoid
- **Using `parseFloat` for invoice amount storage:** The server action already uses `Prisma.Decimal` for all amount fields. Ensure `itemType` and `unitType` are stored as plain strings that match the enum values — Prisma maps them automatically.
- **Computing amounts in the server action with branching logic:** The server action currently does `qty.mul(price)` for all items. For `PERCENT` type, the amount is pre-computed client-side and included in the JSON payload. The server action should trust the client-computed amount (already the pattern — `amount` is sent as part of the item) rather than re-implementing unit logic server-side.
- **Breaking the `itemsJson` hidden field shape:** The hidden field is parsed directly by the server action. Any new fields (`itemType`, `unitType`) must be included in the serialized JSON.
- **Adding `NOT NULL` columns without defaults to existing tables:** `itemType` and `unitType` must have `DEFAULT 'OTHER'` and `DEFAULT 'FLAT'` respectively in the migration to avoid failing on existing rows.

## Common Pitfalls

### Pitfall 1: Prisma Client Out of Sync After Schema Edit
**What goes wrong:** TypeScript compiler reports `itemType` doesn't exist on `InvoiceItem` even though it's in `schema.prisma`.
**Why it happens:** `prisma generate` wasn't run after editing the schema. The `src/generated/prisma/` folder is the generated client — it must be regenerated.
**How to avoid:** Run `npx prisma generate` (from `apps/web/`) immediately after editing `schema.prisma`.
**Warning signs:** Type errors on `invoice.items[0].itemType` in server action or page files.

### Pitfall 2: Validation Package Not Rebuilt
**What goes wrong:** Web app uses stale compiled `.js`/`.d.ts` from `packages/validation/dist/` — new fields silently dropped at validation layer.
**Why it happens:** Turborepo caches builds; editing `packages/validation/src/invoice.ts` doesn't auto-rebuild.
**How to avoid:** Run `npx turbo run build --filter=@drivecommand/validation` after editing the validation source.
**Warning signs:** New optional fields like `bolNumber` parse as `undefined` even when form data is present; no TypeScript errors but runtime data is missing.

### Pitfall 3: FSC Calculation Timing
**What goes wrong:** FSC `unitPrice` auto-fill picks up $0 because the LINEHAUL item's amount hasn't been confirmed yet (user is mid-entry).
**Why it happens:** `getItemAmount` uses `parseFloat` which returns 0 for empty strings.
**How to avoid:** Only auto-fill FSC `unitPrice` when the quick-add button is clicked AND there's at least one LINEHAUL item with a non-zero computed amount. If the user types the LINEHAUL amount after adding FSC, they must update FSC manually (override is always allowed per CONTEXT.md).
**Warning signs:** FSC shows $0 or shows a stale value after linehaul is edited.

### Pitfall 4: PERCENT Calculation Differs From qty * unitPrice
**What goes wrong:** The subtotal is wrong when a PERCENT item is included, because the server action recomputes `amount = qty * unitPrice` without knowing about PERCENT semantics.
**Why it happens:** The current server action does:
```typescript
const amount = qty.mul(price); // qty * price, not (qty/100) * price
```
This is wrong for PERCENT items.
**How to avoid:** Either (a) send the pre-computed `amount` in the itemsJson and use it directly in the server action, bypassing re-computation, OR (b) add unit-type-aware calculation in the server action. Option (a) is cleaner and aligns with how the amount display already works client-side. The server action currently ignores client-sent `amount` and recomputes — this must change for PERCENT items.
**Recommended fix:** Include `amount` in the serialized item JSON, and have the server action use the sent amount directly (trusting client) for all unit types. Alternatively, pass `unitType` and branch in the server action.

### Pitfall 5: `loadedMiles` Precision
**What goes wrong:** `loadedMiles Float?` in Prisma schema maps to `DOUBLE PRECISION` in PostgreSQL. For display and calculation purposes this is fine (miles don't need sub-cent precision), but the migration must use `DECIMAL(10,2)` instead of `DOUBLE PRECISION` to be consistent with the rest of the schema's use of `@db.Decimal`.
**Why it happens:** Prisma `Float` → PostgreSQL `DOUBLE PRECISION`. The CONTEXT.md specifies `Float` but the project convention is `Decimal` for all financial-adjacent numbers.
**How to avoid:** In `schema.prisma`, use `loadedMiles Decimal? @db.Decimal(10, 2)` instead of `Float?`. In migration SQL, use `DECIMAL(10,2)`. If `Float` is intentional (non-financial, display only), this is acceptable — flag for planner to confirm.

### Pitfall 6: Invoice Detail Page Shows Items Without Type Labels
**What goes wrong:** Existing invoice detail page (`[id]/page.tsx`) displays raw item rows with only `description`, `quantity`, `unitPrice`, `amount`. After this phase, items have `itemType` and `unitType` — the detail view should show them but won't unless updated.
**Why it happens:** Page queries `include: { items: true }` so it will get the new fields automatically after regeneration, but the JSX doesn't render them.
**How to avoid:** Update the detail page to show `itemType` labels (humanized) next to each line item description.

### Server Action: Unit-Aware Amount Calculation
```typescript
// apps/web/src/app/(owner)/actions/invoices.ts
// In createInvoice and updateInvoice, replace the amount calculation:
const itemsWithAmounts = result.data.items.map((item) => {
  const qty = new Decimal(item.quantity);
  const price = new Decimal(item.unitPrice);
  let amount: Decimal;
  if (item.unitType === 'PERCENT') {
    // amount = (quantity / 100) * unitPrice
    amount = qty.div(100).mul(price);
  } else {
    // All other unit types: amount = quantity * unitPrice
    amount = qty.mul(price);
  }
  return { ...item, amount };
```

## Load Auto-Populate (Claude's Discretion Recommendation)

**Recommendation: Yes, auto-populate freight details from the linked load.**

The `Load` model already has `weight` (Int?), `commodity` (String?), and `rate` (Decimal) fields. When the invoice form is loaded with a `loadId`, the server can fetch the linked load and pre-fill:
- `commodity` ← `load.commodity`
- `weightLbs` ← `load.weight`
- The load does not have a `pieces` field, so that stays empty.
- `loadedMiles` — not on Load model, leave empty.

This saves data entry without any user-visible complexity. Implementation is straightforward: in the `new/page.tsx` server component, if `loadId` is in searchParams, fetch the load and pass freight fields as `initialData` to `InvoiceForm`.

## Open Questions

1. **`loadedMiles` as `Float` vs `Decimal`**
   - What we know: CONTEXT.md specifies `loadedMiles Float?`. Project convention for all financial/numeric fields is `@db.Decimal`.
   - What's unclear: Is `loadedMiles` used in rate calculations (financial) or purely display?
   - Recommendation: Use `Decimal(10,2)` for consistency with project conventions. Miles to 2 decimal places (e.g., 487.30 miles) is perfectly accurate for billing. Planner should default to `Decimal` unless there's a reason for `Float`.

2. **Server action amount trust model**
   - What we know: Current server action recomputes `amount = qty * price` for all items. This is wrong for PERCENT type.
   - What's unclear: Should the server trust the client-computed amount, or re-compute server-side with unit-type awareness?
   - Recommendation: Add unit-type-aware computation server-side (branch on `unitType`). This is safer than trusting client amounts — prevents manipulation. The formula is simple and deterministic.

3. **Invoice detail page item type display**
   - What we know: The `[id]/page.tsx` detail page does `include: { items: true }` and will automatically receive `itemType`/`unitType` after regeneration.
   - What's unclear: How much UI real estate to give type labels in the detail view.
   - Recommendation: Show `itemType` as a small badge/pill next to each item description in the detail view. Keep it subtle — `OTHER` items show no badge (or a muted one) to avoid cluttering existing invoices.
