## Summary

Phase 37.2 extends the existing mobile owner portal with two feature areas: full route management (list, detail enhancement, create, edit with stop management) and a maintenance module upgrade (scheduled service CRUD, "Due Soon" alerts panel, top-level maintenance screen across all trucks).

The good news is that substantial infrastructure already exists. The route list screen (`(owner)/routes/index.tsx`) and route detail screen (`(owner)/routes/[id].tsx`) are fully built — the detail screen even includes an EditRouteSheet bottom sheet. The service history half of maintenance is already implemented in the truck detail screen with `LogMaintenanceSheet` and a working `GET/POST /api/mobile/owner/trucks/[id]/maintenance` API. What the phase must add is: route creation (new mobile API + multi-step form), route detail enhancement (grouped-by-status list, stop count card display, collapsed status sections), `ScheduledService` CRUD (API + form), a "Due Soon" alerts section, a top-level maintenance screen across all trucks, and a predefined service type picker.

The existing route list uses 4-tab status filter (All/Planned/Active/Completed) but the CONTEXT.md decided on collapsible sections grouped by status. This is the largest UI pattern gap to resolve in planning. The existing EditRouteSheet covers name/status/driver fields but does not yet handle stop management (add/remove/reorder) — that is new work. The `AddressInput` component (`components/owner/AddressInput.tsx`) is complete and ready to embed in stop entry rows.

**Primary recommendation:** Build incrementally on what exists. Route list needs a display change (tabs → collapsible sections) but the fetch infrastructure, FlashList, skeleton, and navigation are all wired up. Scheduled service is net-new but the `ScheduledService` model and safety API already read it — just need dedicated CRUD endpoints and UI.

The web uses a long-scroll form; mobile should use a wizard: Step 1 = name/driver/truck/date, Step 2 = stops.

`react-native-gesture-handler` is already installed. Use `Swipeable` from `react-native-gesture-handler` for stop row deletion. Each stop row renders inside a `Swipeable` with a red "Delete" action revealed on swipe-left. Minimum 2 stops enforced — disable delete when stops.length <= 2.

### Pattern 4: Scheduled Service Due-Soon Logic
The `ScheduledService` model has `baselineDate`, `intervalDays`, `intervalMiles`, `baselineOdometer`. Due-date calculation:
- Date trigger: `baselineDate + intervalDays days`
- Mileage trigger: `baselineOdometer + intervalMiles miles`
- "Due soon" = within 7 days OR within 500 miles of threshold
- "Overdue" = past threshold

This logic lives in the API response — the API should compute and return `dueDate`, `dueMileage`, `status: 'overdue' | 'due_soon' | 'ok'` so the mobile client does no math.

### Pattern 5: Top-Level Maintenance Screen
A new screen at `(owner)/more/maintenance.tsx` shows:
1. "Due Soon" section at top — FlashList of `ScheduledService` items that are overdue or due-soon, grouped or annotated with truck name
2. "Log Service" FAB using `PageSpeedDial` pattern
3. Truck filter dropdown or horizontal scroll tabs to filter by truck

This requires a new API endpoint `GET /api/mobile/owner/maintenance` (cross-truck view) that returns upcoming services across all trucks in the tenant with computed due status.

### Anti-Patterns to Avoid
- **Free-text service type input:** The CONTEXT.md locks this — predefined list only. Use a picker sheet, not TextInput.
- **FlatList for stop list:** Use ScrollView inside the bottom sheet (stop list is bounded, not infinite). FlashList is overkill here and has edge cases inside BottomSheet.
- **Tabs for route list:** Decision is collapsible sections, not the existing 4-tab pattern. The existing tabs implementation must be replaced.
- **Blocking edit on active routes:** CONTEXT.md explicitly allows full edit on IN_PROGRESS routes. Do not add "route is active, cannot edit" guards.
- **`user_metadata` for auth claims:** All auth reads must use `app_metadata` (enforced at API layer, already correct in all existing mobile endpoints).

## Common Pitfalls

### Pitfall 1: Stop Management Inside BottomSheet
**What goes wrong:** Rendering `Swipeable` rows inside a `ScrollView` inside a `BottomSheet` causes gesture conflicts — vertical scroll steals horizontal swipe events.
**Why it happens:** Gesture handler priority. GestureHandler's Swipeable and RN's ScrollView compete.
**How to avoid:** Set `simultaneousHandlers` on Swipeable, or use `directionalLockEnabled={true}` on ScrollView. Alternatively, don't nest swipeable rows inside the sheet's scroll — put stops as a fixed section above the scroll.
**Warning signs:** Swipe gesture gets cancelled immediately on first touch.

### Pitfall 2: AddressInput Dropdown z-Index Inside BottomSheet
**What goes wrong:** AddressInput renders its dropdown with `position: absolute`, which clips inside parent containers with `overflow: hidden`.
**Why it happens:** RN's z-index stacking doesn't work the same as web CSS. The BottomSheet or ScrollView may clip the dropdown.
**How to avoid:** The existing `AddressInput` uses `zIndex: 50` and `position: absolute`. Do NOT wrap each stop row's AddressInput in `overflow: hidden` containers. Each stop row should have explicit z-index ordered by reverse position (bottom stop gets lower z-index than top stop).
**Warning signs:** Dropdown appears clipped or behind other stop rows.

### Pitfall 3: Route Creation — Driver Scheduling Conflict
**What goes wrong:** Creating a route for a driver who already has a non-completed route on the same date will fail.
**Why it happens:** The web `createRoute` action checks for conflicting routes on the same scheduledDate (same UTC day window). The mobile POST API must implement the same check.
**How to avoid:** Implement the conflict check in the POST API handler (same logic as in `apps/web/src/app/(owner)/actions/routes.ts` lines 121-138). Return a clear error message the mobile form can surface.
**Warning signs:** Silent 500s on route creation in certain driver/date combinations.

### Pitfall 4: ScheduledService Model Fields vs. UI Expectations
**What goes wrong:** The `ScheduledService` model uses `baselineDate` + `intervalDays` (not a direct `dueDate`). Computing `dueDate = baselineDate + intervalDays` must happen server-side.
**Why it happens:** The model is designed for recurring intervals, not one-off scheduling. But the CONTEXT.md decision is to let owners set a due date — which means `intervalDays = daysBetween(now, dueDate)` and `baselineDate = now` for a one-off.
**How to avoid:** The scheduled service creation form should collect `dueDate` (date picker) and `dueMileage` (number). The API converts: `baselineDate = now`, `intervalDays = daysUntilDueDate`, `baselineOdometer = currentTruckOdometer`, `intervalMiles = dueMileage - currentOdometer`. Return a user-friendly `dueDate` and `dueMileage` in GET responses.
**Warning signs:** Dates display as unexpected values when viewing scheduled services after creation.

### Pitfall 5: Route List Display Change (Tabs → Sections)
**What goes wrong:** The existing route list makes a single API call with `status` filter. With collapsible sections, you need either 3 separate queries (one per status group) or one `all` query then client-side grouping.
**Why it happens:** The tab pattern was designed around server-side filtering. Sections require all data at once.
**How to avoid:** Use a single `getRoutes(token, 'all')` call, then group client-side by `status`. Pagination may need adjustment — the current API returns up to 50 routes, which is sufficient for the owner portal where route counts are small.
**Warning signs:** "Active" section empty while data exists, or sections not updating on refresh.

### Pitfall 6: Truck Picker in Route Create Form
**What goes wrong:** Route creation requires selecting a truck. The existing `TruckPickerSheet` component exists but may include trucks already "In Use" or "In Maintenance".
**Why it happens:** The current picker fetches from `ownerApi.getTrucks()` which returns all non-archived trucks with computed status.
**How to avoid:** Show all trucks in the picker but visually indicate "In Use" or "In Maintenance" status so the owner can make an informed choice. Do not block selection based on truck status (business rule: owner can decide).

### Due-Soon Computation (Server-Side)
```typescript
// In API response serialization for ScheduledService
function computeServiceStatus(
  svc: ScheduledService,
  currentOdometer: number,
  now: Date
): 'overdue' | 'due_soon' | 'ok' {
  const DUE_SOON_DAYS = 7
  const DUE_SOON_MILES = 500

  if (svc.intervalDays) {
    const dueDate = addDays(svc.baselineDate, svc.intervalDays)
    const daysLeft = differenceInDays(dueDate, now)
    if (daysLeft < 0) return 'overdue'
    if (daysLeft <= DUE_SOON_DAYS) return 'due_soon'
  }
  if (svc.intervalMiles) {
    const dueMileage = svc.baselineOdometer + svc.intervalMiles
    const milesLeft = dueMileage - currentOdometer
    if (milesLeft < 0) return 'overdue'
    if (milesLeft <= DUE_SOON_MILES) return 'due_soon'
  }
  return 'ok'
}
```

## Open Questions

1. **Stop type in route create form**
   - What we know: RouteStopType enum has only `PICKUP` and `DELIVERY`. The web form allows setting type per stop.
   - What's unclear: Does the CONTEXT.md step-by-step UX mean stops auto-assign type (first = PICKUP, last = DELIVERY, middle = ?), or does the user pick per-stop?
   - Recommendation: Default first stop to PICKUP, last stop to DELIVERY, middle stops to PICKUP. Allow user to toggle type per stop via a simple toggle/button. This matches web behavior.

2. **"View All" maintenance history on truck detail**
   - What we know: Current truck detail shows only the top 5 maintenance events. Full history is available via the same API (50 events).
   - What's unclear: Should the truck detail show all events (now scrollable) or link to a separate full-history screen?
   - Recommendation: Show all events in the service history section (remove the `.slice(0, 5)` cap). The section is already inside a ScrollView so length is not a UX problem.

3. **More menu entry for Maintenance**
   - What we know: `more/index.tsx` has a FLEET section with Routes, Trucks, Compliance, Fuel Log, Safety.
   - What's unclear: Does Maintenance get its own top-level row in the More menu, or is it discoverable only via Trucks?
   - Recommendation: Add a "Maintenance" row to the FLEET section in the More menu (the CONTEXT.md explicitly requires a top-level maintenance area as a second entry point).

4. **Scheduled service completion flow**
   - What we know: `ScheduledService.isCompleted` + `completedAt`. CONTEXT.md says Claude's discretion.
   - Recommendation: "Mark Complete" button on each scheduled service card. On tap, shows a confirmation bottom sheet asking for the actual service date and odometer reading. On confirm, creates a `MaintenanceEvent` record (the actual history entry) AND sets `isCompleted=true` on the scheduled service. This gives a clean audit trail — scheduled service becomes history.
