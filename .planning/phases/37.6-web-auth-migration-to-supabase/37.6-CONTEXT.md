# Phase 37.6: Web Auth Migration to Supabase - Context

**Gathered:** 2026-03-31
**Status:** Ready for planning

<domain>
## Phase Boundary

Replace the custom AES-256-GCM encrypted session cookie system in the web app with Supabase Auth, so both web and mobile share a single authentication provider. All three portals (Owner, Driver, SysAdmin) must continue working correctly after migration. The custom session system (`src/lib/auth/session.ts`, `encrypt`/`decrypt`, `requireAuth`/`requireRole`) is removed entirely. No new auth features (MFA, SSO, magic link) are in scope — this is a like-for-like replacement on the web side only.

</domain>

<decisions>
## Implementation Decisions

### Session continuity
- Clean cutover — no migration of existing session data
- All existing web sessions are invalidated at deploy time
- Users log in fresh after migration (no silent re-auth, no redirect tricks)
- Acceptable because there are no real production users yet

### SysAdmin handling
- SysAdmin users get a Supabase Auth account like any other user
- `isSystemAdmin: true` stored in Supabase `app_metadata` (admin-controlled, cannot be set by the user themselves)
- Same Supabase Auth provider as Owner/Driver — no separate system
- `app_metadata.isSystemAdmin` maps to a custom JWT claim readable server-side without an extra DB lookup
- SysAdmin creation happens via Supabase service role (not via the app's signup flow)

### Rollout strategy
- All three portals migrated simultaneously in a single atomic deployment
- No feature flags, no phased rollout, no dual auth period
- Rationale: no production traffic to protect; parallel auth systems mid-migration are more dangerous than a clean swap
- One deploy = old auth gone, Supabase auth live

### Tenant isolation post-migration
- `tenantId` stored in Supabase `app_metadata` as a custom JWT claim
- Set at user creation time via service role (owner/driver invite flow writes tenantId to app_metadata)
- Available in every JWT without a DB lookup — replaces the cookie decrypt step
- Admin-controlled field — users cannot tamper with their own tenantId
- Aligns exactly with how mobile already reads tenant context from the JWT
- The `bypass_rls` pattern remains — tenantId from JWT claim is passed to Prisma queries as `where: { tenantId }`

### Web auth architecture post-migration
- Remove: `src/lib/auth/session.ts` (encrypt/decrypt/getSession/setSession)
- Remove: `AUTH_SECRET` environment variable
- Add: Supabase Auth client (server-side) using service role for admin operations
- Replace `requireAuth()`/`requireRole()` with helpers that verify Supabase JWT and extract claims
- Middleware updated to verify Supabase JWT for web routes (mobile routes already handled separately)
- Cookie replaced by Supabase's own session management (httpOnly cookie via `@supabase/ssr`)

### Claude's Discretion
- Exact helper function signatures for `requireAuth`/`requireRole` replacements
- How to structure the Supabase SSR client setup (server components vs route handlers vs middleware)
- Error page/redirect behavior on auth failure
- How the invite flow (owner invites driver) is updated to write `tenantId` to `app_metadata`

</decisions>

<specifics>
## Specific Ideas

- Safety is the top priority — the migration should be conservative, not clever
- The mobile JWT auth pattern is the reference implementation; web should mirror it as closely as possible
- `@supabase/ssr` is the correct package for Next.js App Router cookie-based Supabase sessions
- After migration, a single `src/lib/auth/supabase.ts` should replace the entire old `src/lib/auth/` directory

</specifics>

<deferred>
## Deferred Ideas

- MFA / two-factor authentication — post-launch, v6.0
- Magic link / passwordless login — post-launch, v6.0
- SSO / OAuth providers — post-launch, v6.0
- Session activity logging — post-launch

</deferred>
