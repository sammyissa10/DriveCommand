# Phase 37.6 Plan 01: Security Claims to app_metadata Migration Summary

Security claims (role, tenantId, isSystemAdmin, permissions) moved from user-writable user_metadata to admin-only app_metadata across all 6 auth files, closing a privilege escalation vector where users could overwrite their own role.

## What Was Built

### Task 1: Security Claims Migration

The root security gap was that `user_metadata` is writable by any authenticated user via `supabase.auth.updateUser()`. Any user could escalate their own `role`, `tenantId`, or `isSystemAdmin` claim.

**accept-invitation/route.ts** — The only non-sysadmin user creation path. Split the `admin.auth.admin.createUser()` call:
- `user_metadata`: `firstName`, `lastName` only (display fields, user-editable is acceptable)
- `app_metadata`: `role`, `tenantId`, `isSystemAdmin: false`, `permissions` (admin-only, tamper-proof)

**session.ts** — Introduced dual-source pattern:
```typescript
const appMeta = user.app_metadata || {};
const userMeta = user.user_metadata || {};
```
Security claims read from `appMeta`, display fields from `userMeta`. Updated JSDoc.

**middleware.ts** — All security claim reads (`tenantId`, `isSystemAdmin`, `role`, `permissions`) switched from `user.user_metadata` to `user.app_metadata`. Added clarifying comment.

**login/route.ts** — Security claims (`isSystemAdmin`, `role`, `tenantId`) from `appMeta`. Display fields (`firstName`, `lastName`) from `userMeta` for the `name` field.

**me/route.ts** — Both code paths updated:
- Bearer (mobile): `admin.auth.getUser(token)` — reads security claims from `appMeta`
- Cookie (web): `supabase.auth.getUser()` — same split pattern

**mobile-auth.ts** — `meta` variable renamed to `appMeta`, reads from `user.app_metadata`. Updated JSDoc to document the security rationale.
