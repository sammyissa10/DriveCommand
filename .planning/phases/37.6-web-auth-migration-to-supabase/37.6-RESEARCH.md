## Summary

**Critical discovery: The quick-109 task (commit `94b1c70`, March 25 2026) already completed the core Supabase Auth migration.** The AES-256-GCM encrypted session cookie system was removed entirely. The current codebase uses `@supabase/ssr` for cookie-based sessions, `supabase.auth.signInWithPassword` for login, `supabase.auth.signOut` for logout, and `supabase.auth.getUser()` in middleware and server components. There is no `encrypt`/`decrypt` function remaining in source code. `AUTH_SECRET` is present in `.env` files but is not referenced anywhere in TypeScript source — it is a dead env var.

**The remaining work for Phase 37.6 is targeted hardening,** not a ground-up migration. The primary security gap is that `tenantId`, `isSystemAdmin`, and other claims are currently written to `user_metadata` (user-editable) instead of `app_metadata` (admin-only, tamper-proof). The CONTEXT.md decisions specify `app_metadata` for all admin-controlled claims. This affects every user creation path: the `accept-invitation` POST route, the `createTenant` admin action, and any future sysadmin creation utilities. Additionally, several source files contain stale comments referencing "session decrypts" (a leftover from the old AES system) and the CONTEXT specifies consolidating the `src/lib/auth/` directory into a single `src/lib/auth/supabase.ts`.

**Primary recommendation:** Phase 37.6 is a 3-task hardening pass: (1) migrate all user creation from `user_metadata` to `app_metadata` for admin-controlled claims, (2) remove `AUTH_SECRET` from all env files, and (3) optionally consolidate auth helpers per CONTEXT spec. The existing `@supabase/ssr` setup, middleware, and API routes are already correct and do not need replacement.

## Architecture Patterns

### Current Auth Flow (already implemented)

```
Browser → POST /api/auth/login
  → supabase.auth.signInWithPassword({ email, password })
  → @supabase/ssr sets httpOnly cookie automatically
  → Returns { redirectUrl, token, refreshToken, user }
  → window.location.href = redirectUrl

Every request → middleware.ts
  → createMiddlewareClient(request)
  → supabase.auth.getUser()  ← verifies JWT, refreshes session if needed
  → Extracts meta from user.user_metadata
  → Injects x-tenant-id header
  → Returns response with refreshed cookies

Server Component / Action → getSession()
  → createSupabaseServerClient()
  → supabase.auth.getUser()
  → Returns SessionData from user.user_metadata
```

### The app_metadata vs user_metadata Gap

**This is the central work of Phase 37.6.**

In Supabase Auth:
- `user_metadata` — user-editable. Any authenticated user can call `supabase.auth.updateUser({ data: { tenantId: 'other-tenant' } })` and overwrite it.
- `app_metadata` — admin-only. Can only be written by service role (`admin.auth.admin.updateUserById`). Users cannot tamper with it. It appears in the JWT as the `app_metadata` claim.

The CONTEXT.md specifies that `tenantId`, `isSystemAdmin`, `role`, and `permissions` must be in `app_metadata`. Currently, all these are written to `user_metadata` in `accept-invitation/route.ts`:

```typescript
// CURRENT (insecure — user_metadata is user-writable):
await admin.auth.admin.createUser({
  email: userEmail,
  password,
  email_confirm: true,
  user_metadata: {
    role: userRole,
    tenantId: invitation.tenantId,
    firstName: invitation.firstName,
    // ...
  },
});

// TARGET (secure — app_metadata is admin-only):
await admin.auth.admin.createUser({
  email: userEmail,
  password,
  email_confirm: true,
  user_metadata: {
    firstName: invitation.firstName,
    lastName: invitation.lastName,
  },
  app_metadata: {
    role: userRole,
    tenantId: invitation.tenantId,
    isSystemAdmin: false,
    permissions: userRole === 'MANAGER' ? (invitation.permissions ?? null) : null,
  },
});
```

After this change, all readers (`session.ts`, `middleware.ts`, login route, etc.) must switch from `user.user_metadata` to `user.app_metadata` for the admin-controlled claims.

### SessionData Shape (unchanged)

The `SessionData` interface in `session.ts` remains the same — only the metadata source changes:

```typescript
// session.ts — only the metadata read source changes:
const meta = user.app_metadata || {};  // was: user.user_metadata
return {
  userId: user.id,
  email: user.email!,
  role: meta.role || 'DRIVER',
  tenantId: meta.tenantId || '',
  firstName: meta.firstName,      // firstName/lastName can stay in user_metadata (non-sensitive)
  lastName: meta.lastName,
  isSystemAdmin: meta.isSystemAdmin || false,
  permissions: meta.permissions,
};
```

Note: `firstName` and `lastName` are not security-sensitive and can remain in `user_metadata` (user-editable display fields). The security-critical fields are: `role`, `tenantId`, `isSystemAdmin`, `permissions`.

### SysAdmin Creation Path

SysAdmin users have no in-app creation flow. Per the CONTEXT decision, they are created via service role. The planner should include a one-time utility (a standalone script or an admin-only API endpoint) that creates a sysadmin via:

```typescript
await admin.auth.admin.createUser({
  email: 'sysadmin@drivecommand.com',
  password: '...',
  email_confirm: true,
  user_metadata: { firstName: 'System', lastName: 'Admin' },
  app_metadata: {
    isSystemAdmin: true,
    role: 'OWNER',  // fallback role — sysadmin middleware check uses isSystemAdmin, not role
  },
});
```

The Prisma `User` table does NOT need a matching row for sysadmin (they have no tenant). The middleware already handles `!meta.tenantId && meta.isSystemAdmin` correctly (skips the onboarding redirect).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead |
|---------|-------------|-------------|
| Session cookie management | Custom httpOnly cookie logic | `@supabase/ssr` createServerClient — already handles this |
| Token refresh | Manual refresh logic | `@supabase/ssr` middleware client calls `getUser()` which auto-refreshes |
| JWT verification | Manual JWT decode/verify | `supabase.auth.getUser()` — cryptographically verifies against Supabase's public key |
| Admin-controlled metadata | Custom signed claims | Supabase `app_metadata` — admin-only, appears in JWT automatically |

**Key insight:** The `@supabase/ssr` pattern (createServerClient in middleware, createServerClient in server components) handles the entire session lifecycle. The existing implementation in `apps/web/src/lib/supabase/` is the correct pattern — do not replace it.

## Common Pitfalls

### Pitfall 1: Reading app_metadata vs user_metadata in the Wrong Accessor

**What goes wrong:** After migrating writes to `app_metadata`, the reads in `session.ts` and `middleware.ts` still reference `user.user_metadata`, so `tenantId`, `role`, etc. come back as `undefined`.

**How to avoid:** Update ALL four read sites atomically with the write changes. The migration is not complete until both the write (in `accept-invitation`) and all reads are updated together.

**Warning signs:** `session.tenantId` is empty string, middleware redirects everyone to `/onboarding`, all server actions throw "Tenant context is required".

### Pitfall 2: Losing firstName/lastName by Moving Everything to app_metadata

**What goes wrong:** Moving `firstName` and `lastName` to `app_metadata` means users can no longer update their display name via the standard Supabase `updateUser` call. It also requires a service role call to update names.

**How to avoid:** Keep `firstName` and `lastName` in `user_metadata`. Only the security-critical fields (`role`, `tenantId`, `isSystemAdmin`, `permissions`) need to be in `app_metadata`. The `session.ts` reads can merge from both:

```typescript
const appMeta = user.app_metadata || {};
const userMeta = user.user_metadata || {};
return {
  userId: user.id,
  email: user.email!,
  role: appMeta.role || 'DRIVER',
  tenantId: appMeta.tenantId || '',
  firstName: userMeta.firstName,     // display field — user-editable is fine
  lastName: userMeta.lastName,
  isSystemAdmin: appMeta.isSystemAdmin || false,
  permissions: appMeta.permissions,
};
```

### Pitfall 3: Forgetting the Login Route Reads Metadata

**What goes wrong:** `accept-invitation` is updated to write `app_metadata`, and `session.ts`/`middleware.ts` are updated to read `app_metadata`. But `src/app/api/auth/login/route.ts` still reads `user.user_metadata` for `role`, `isSystemAdmin`, and `tenantId` to build the redirect URL and return user context.

**How to avoid:** Include `login/route.ts` in the metadata reader update. The login route reads metadata to determine the redirect URL (`/dashboard`, `/my-route`, or `/admin-dashboard`) — if it reads from `user_metadata`, all values will be undefined after the migration.

### Pitfall 4: AUTH_SECRET Still in env Causes Confusion

**What goes wrong:** `AUTH_SECRET` remains in `.env`, `.env.example`, and `.env.local` after migration. Developers (and CI) see it and assume it's still used, or future code accidentally references it.

**How to avoid:** Remove `AUTH_SECRET` from all four env files: `.env`, `.env.local`, `.env.example`, and `.vercel/.env.development.local`.

### Pitfall 5: me/route.ts Mobile Path Reads user_metadata

**What goes wrong:** `/api/auth/me` has two code paths — Bearer token (mobile) and cookie (web). The mobile path also reads from `user.user_metadata`. After the migration, the mobile path will also return empty `role`/`tenantId`.

**How to avoid:** Update both code paths in `me/route.ts`. The mobile path uses `admin.auth.getUser(bearerToken)` — the returned user object has the same `.app_metadata` / `.user_metadata` structure.

### Reading from Both Metadata Sources (Recommended Pattern)

```typescript
export const getSession = cache(async function getSession(): Promise<SessionData | null> {
  const { createSupabaseServerClient } = await import('@/lib/supabase/server');
  const supabase = await createSupabaseServerClient();
  const { data: { user } } = await supabase.auth.getUser();
  if (!user) return null;

  const appMeta = user.app_metadata || {};   // admin-controlled claims
  const userMeta = user.user_metadata || {}; // user-editable display fields
  return {
    userId: user.id,
    email: user.email!,
    role: appMeta.role || 'DRIVER',
    tenantId: appMeta.tenantId || '',
    firstName: userMeta.firstName,
    lastName: userMeta.lastName,
    isSystemAdmin: appMeta.isSystemAdmin || false,
    permissions: appMeta.permissions,
  };
});
```
