## Summary

Phase 37.1 adds two self-contained features to the driver mobile portal. Both features have clear reference implementations in the web app and well-established existing mobile patterns to follow. The work is primarily UI composition — no new data models are needed.

The **My Route screen** has a complete reference in `apps/web/src/app/(driver)/my-route/page.tsx`. The route data shape is already understood: `getMyAssignedRoute()` returns a route with `loads[]`, `truck`, `stops[]`, and the FleetMessage schema has a `routeId` field enabling route-scoped messaging. The mobile API does not yet have a `/api/mobile/driver/route` endpoint — this must be created. Route-scoped messages need a new `/api/mobile/driver/messages/route` endpoint pattern (modeled on the existing driver messages endpoint but filtering by `routeId`).

The **Support Ticket FAB** has a complete web reference in `apps/web/src/components/support/support-ticket-modal.tsx`. The mobile equivalent uses the existing `BottomSheet` component (already available), the `react-native-toast-message` library (already installed at ^2.3.3), and a new `/api/mobile/support/ticket` REST endpoint. The web `createSupportTicket` server action cannot be called from mobile — it uses Next.js session auth. A new mobile API route with Bearer token auth is required.

**Primary recommendation:** Build the two features in order — route API endpoint first, then My Route screen, then support ticket API endpoint, then FAB + form. Each builds on the previous.

### Anti-Patterns to Avoid
- **Do NOT use `<Modal>` directly for the support ticket form** — the existing `BottomSheet` component handles Modal, animation, backdrop, and keyboard avoidance. Wrapping it yourself duplicates complexity.
- **Do NOT call the web `createSupportTicket` server action from mobile** — it uses `getSession()` (session-cookie auth), not Bearer tokens. The mobile app must hit a REST endpoint.
- **Do NOT add the FAB inside individual screen files** — the layout Fragment pattern is the correct approach. Adding to each screen would create z-index stacking issues and duplicate state.
- **Do NOT use `usePathname` from `react-navigation`** — use it from `expo-router` which is already the app's routing library.
- **Do NOT reuse `StopTimelineItem` for route loads** — `StopTimelineItem` is for `RouteStop` (address, type, scheduledAt). Route loads have a different shape (loadNumber, origin, destination, status). A new `RouteLoadTimelineItem` component is needed.
- **Do NOT add `routeId` filtering to the existing `/api/mobile/driver/messages` endpoint** — that endpoint returns ALL driver messages. The route thread needs a separate endpoint to avoid breaking the Messages tab.

## Common Pitfalls

### Pitfall 1: BottomSheet keyboard behavior on description field
**What goes wrong:** The description `TextInput` (multiline, 2000 char max) causes the BottomSheet to be obscured by the keyboard on Android.
**Why it happens:** `BottomSheet` uses `KeyboardAvoidingView` with `behavior: Platform.OS === 'ios' ? 'padding' : 'height'`. On Android, `height` reduces the sheet height but may not scroll the focused input into view.
**How to avoid:** Wrap the form content in a `ScrollView` inside the BottomSheet so the description field can scroll above the keyboard. The BottomSheet's content area (`flex: 1, paddingHorizontal: 16, paddingTop: 16`) already supports this — just add a `ScrollView` around the form fields.
**Warning signs:** Testing shows description field hidden behind keyboard on Android emulator.

### Pitfall 2: FAB z-index over modal content
**What goes wrong:** If the BottomSheet opens and the FAB still appears on top of the backdrop overlay, it creates a visual layering bug.
**Why it happens:** The FAB uses `position: absolute` within the Fragment layout. The BottomSheet renders a `Modal` (which by default has `zIndex` handled by RN's Modal system). On Android, RN Modals always render above non-modal views, so this is naturally resolved. On iOS, ensure the FAB does not use a zIndex higher than the modal's `statusBarTranslucent` rendering layer.
**How to avoid:** The FAB triggers the BottomSheet's `visible` state — when sheet is open, the FAB is still rendered but behind the modal. This is the correct behavior (Modal system handles it). Do not add explicit `zIndex` to the FAB's container.
**Warning signs:** FAB visible on top of backdrop on iOS simulator.

### Pitfall 3: Missing route API endpoint — driverApi.getMyRoute does not exist
**What goes wrong:** The driver API client (`packages/api-client/src/driver.ts`) has NO route-fetching function. The web uses server actions (`getMyAssignedRoute()`). Mobile needs a dedicated REST endpoint.
**Why it happens:** Phase 37 (completed) was load-focused. No route endpoint was added.
**How to avoid:** Create `/api/mobile/driver/route/route.ts` (GET) as the first task. Then add `getMyRoute()` to `driverApi`. The React Query call in `RouteCard` and `my-route.tsx` both depend on this.
**Warning signs:** TypeScript errors on `driverApi.getMyRoute` until endpoint + client are added.

### Pitfall 4: Route loads vs. route stops — different data shapes
**What goes wrong:** Confusing `route.stops` (RouteStop[] — physical stop addresses) with `route.loads` (Load[] — linked loads).
**Why it happens:** The web page shows both in different sections. The mobile route screen only shows loads (as a timeline), not stops.
**How to avoid:** The API endpoint for `/api/mobile/driver/route` should include `loads` in the Prisma `include` (same as `getMyAssignedRoute()` on the web). The mobile UI timeline maps over `route.loads`, not `route.stops`.
**Data shape reference:**
```typescript
// route.loads[] — what we display in the mobile timeline
{ id: string, loadNumber: string, origin: string, destination: string, status: string }

// route.stops[] — physical addresses (NOT displayed in mobile; left for future)
{ id: string, type: 'PICKUP'|'DELIVERY', address: string, status: 'PENDING'|'ARRIVED'|'DEPARTED', position: number }
```

### Pitfall 5: Route messages — separate endpoint needed
**What goes wrong:** Reusing the existing `/api/mobile/driver/messages` endpoint for route messages would mix route thread messages with load-thread messages in the Messages tab.
**Why it happens:** `FleetMessage` has both `loadId` and `routeId` fields. The Messages tab fetches ALL driver messages from one endpoint.
**How to avoid:** Create a separate `/api/mobile/driver/messages/route-thread?routeId=` endpoint that filters by `routeId`. This endpoint is only called from the My Route screen's messages section, not the Messages tab. When sending a route message, set `routeId` (not `loadId`).

### Pitfall 6: `usePathname` returns route group path, not clean display path
**What goes wrong:** On the My Route screen, `usePathname()` returns `/(driver)/loads/my-route`, which includes the route group prefix `(driver)`.
**Why it happens:** Expo Router's `usePathname()` returns the full filesystem path including group segments.
**How to avoid:** Pass the `pathname` string as-is to `fromPage`. The sysadmin support ticket view already displays raw paths — this is fine. No transformation needed.

### Pitfall 7: FlashList `ListHeaderComponent` causes re-render loop
**What goes wrong:** If `ListHeaderComponent` is defined as an inline JSX element, FlashList re-renders on every parent render, causing the RouteCard query to refetch.
**Why it happens:** Inline JSX creates new object reference on every render.
**How to avoid:** Memoize the header:
```typescript
const listHeader = useMemo(
  () => route ? <RouteCard route={route} onPress={handleRoutePress} /> : null,
  [route, handleRoutePress]
)
// Then: ListHeaderComponent={listHeader}
```

## Open Questions

1. **Should `RouteCard` on the Loads tab fetch route data independently, or share the query with the My Route screen?**
   - What we know: The Loads tab currently fetches loads via `useQuery(['driver-loads', activeTab])`. The RouteCard will need its own query.
   - What's unclear: Whether to use `queryKey: ['driver-route']` in `RouteCard` only, or also prefetch it in `_layout.tsx` for the My Route screen.
   - Recommendation: Use a shared `queryKey: ['driver-route']` in both `RouteCard` (on loads tab) and `my-route.tsx`. TanStack Query's cache deduplicates requests — if both are mounted simultaneously, only one network call fires. The My Route screen `useQuery` will get a cache hit from the RouteCard's prior fetch. No prefetch needed in the layout.

2. **Should route messages inline use the same `MessageBubble` component as the Messages tab?**
   - What we know: `MessageBubble` is defined inline in `messages.tsx` (not exported).
   - What's unclear: Should it be extracted to a shared component or duplicated?
   - Recommendation: Extract `MessageBubble` to `components/driver/MessageBubble.tsx` and import it in both `messages.tsx` and the route messages section in `my-route.tsx`. This avoids duplication without over-engineering.

3. **Does the support ticket API need to fire the email notification?**
   - What we know: The web `createSupportTicket` action calls `sendNewTicketNotification()` (fire-and-forget).
   - What's unclear: Whether the mobile endpoint should replicate this.
   - Recommendation: Yes — replicate the fire-and-forget email notification in the mobile endpoint. The sysadmin team should know about tickets from mobile users. Same `sendNewTicketNotification()` call, wrapped in try/catch to not block the response.
