## Migration Conventions

**Location:** `apps/web/prisma/migrations/<timestamp>_<slug>/migration.sql`

**Naming pattern:** `YYYYMMDDHHMMSS_<descriptor>` where the timestamp is 14 digits followed by an underscore and a lowercase snake_case slug.

Recent examples:
- `20260429000001_tenant_self_onboarding/migration.sql`
- `20260429000002_seed_plans_and_automations/migration.sql`
- `20260425030001_phase46_playbook_step_overdue_fields/migration.sql`

**How migrate.mjs works (source: `apps/web/scripts/migrate.mjs`):**
- Reads `prisma/migrations/` directory, sorts lexicographically (timestamp-prefixed names sort chronologically)
- Tracks applied migrations in `_prisma_migrations` table
- Each migration directory must contain `migration.sql`
- Wraps each migration file in its own `BEGIN` / `COMMIT` transaction
- The SQL file itself must NOT include `BEGIN`/`COMMIT` — the script provides them
- Idempotency is enforced via `IF NOT EXISTS` / `DO $$ BEGIN … EXCEPTION WHEN duplicate_object` blocks
- Uses `DIRECT_URL` env var (not the pooled `DATABASE_URL`) for migration runs

**SQL format for additive columns (established pattern from `20260429000001_tenant_self_onboarding`):**
```sql
ALTER TABLE carrier_trucks ADD COLUMN IF NOT EXISTS is_sample BOOLEAN NOT NULL DEFAULT false;
```

## Existing Seeder

**File:** `apps/web/src/lib/onboarding/seed-sample-data.ts`

**Signature:**
```typescript
export async function seedSampleData(
  tx: TX,               // Prisma.TransactionClient
  tenantId: string,
  tenantSlug: string,
  bucket: FleetSizeBucket,
  ownerUserId: string,

```

**Transaction pattern:** Receives `tx: TX` from the caller — the seeder does NOT open its own transaction. It receives a `Prisma.TransactionClient` that the caller (provisioning code) opens with `prisma.$transaction(async (tx) => { ... }, TX_OPTIONS)`. The transaction includes `set_config('app.bypass_rls', 'on', TRUE)` set by the caller before invoking seedSampleData.

**Fleet-size fork logic:**
```typescript
const SEED_CONFIGS: Record<FleetSizeBucket, SeedConfig> = {
  OWNER_OPERATOR: { trucksCount: 1, driversCount: 1, customersCount: 1 },
  SMALL:          { trucksCount: 3, driversCount: 3, customersCount: 2 },
  MEDIUM:         { trucksCount: 3, driversCount: 3, customersCount: 2 },
  LARGE:          { trucksCount: 3, driversCount: 3, customersCount: 2 },
};
```

Loads: OWNER_OPERATOR = 2 loads (1 DELIVERED + 1 IN_TRANSIT); others = 3 loads (1 DELIVERED + 2 IN_TRANSIT).

**What it currently writes (PascalCase — OLD):**
- `tx.truck.create(...)` — PascalCase Truck model
- `tx.user.create(...)` — sample driver Users (isSample=true, role=DRIVER, no Supabase Auth identity)
- `tx.customer.create(...)` — PascalCase Customer model
- `tx.load.create(...)` — PascalCase Load model

**Sample driver approach in current seeder:** Creates User rows only (no carrier_drivers row). Password set to `'SAMPLE—NOT_A_REAL_LOGIN'` (bcrypt-unmatchable placeholder). The Phase 50 rewrite must ALSO create a `CarrierDriver` row for each sample driver.

**Kill switch not yet implemented.** Phase 50-02 adds `ONBOARDING_SEED_SAMPLES` env var.

## Existing Activation Tracker

**File:** `apps/web/src/lib/onboarding/activation-tracker.ts`

**Signature:**
```typescript
export async function recordActivationEvent(
  tenantId: string,
  event: ActivationEventType
): Promise<void>
```

**Event types:**
```typescript
type ActivationEventType =
  | 'first_real_truck'
  | 'first_real_driver'
  | 'first_real_client'
  | 'first_load_in_transit';
```

**Field map:**
```typescript
const FIELD_MAP: Record<ActivationEventType, string> = {
  first_real_truck:      'firstRealTruckAt',
  first_real_driver:     'firstRealDriverAt',
  first_real_client:     'firstRealClientAt',
  first_load_in_transit: 'firstLoadInTransitAt',
};
```

**completionPct formula:**
```
completionPct = 20 * (1 + truckDone + driverDone + clientDone + transitDone)
```
Starts at 20% (accountCreated counts as 1). Reaches 100% when all 4 events are recorded.

**Transaction pattern:** Opens its own `prisma.$transaction(async (tx) => { ... }, TX_OPTIONS)` and sets bypass_rls itself:
```typescript
await tx.$executeRaw`SELECT set_config('app.bypass_rls', 'on', TRUE)`;
```

**Error handling:** NEVER propagates errors. The catch block writes an `activation.tracker.error` AppEvent on a separate connection. The caller's action succeeds regardless.

**Idempotency:** Each field is only written once (skips if already set):
```typescript
const currentFieldValue = current[field as keyof typeof current];
if (currentFieldValue !== null && currentFieldValue !== undefined) return;
```

**Uses `prisma` directly** (not a tx passed in) — it is called from `after()` blocks or top-level, not inside an open transaction.

## first_real_driver Flow (invitation acceptance chain)

**Definitive answer: YES — the accept-invitation flow covers Carrier Ops drivers.**

**Evidence from `apps/web/src/app/api/auth/accept-invitation/route.ts` (lines 237–258):**


And the activation tracker call (lines 252–258):
```typescript
// Activation tracker: fire for real drivers (invitation flow always creates real users)
if (userRole === 'DRIVER') {
  try {
    await recordActivationEvent(invitation.tenantId, 'first_real_driver');
  } catch (err) {
    console.error('[accept-invitation] activation tracker failed', err);
  }
}
```

**Flow:** Owner creates a CarrierDriver record via `POST /api/v1/carrier/fleet/drivers` (no tracker call there currently). When the driver accepts their invitation via `/api/auth/accept-invitation`, the accept-invitation handler:
1. Creates the Supabase Auth user + Prisma User row
2. Links the existing CarrierDriver row to the new User (via `updateMany` on email match)
3. Calls `recordActivationEvent(tenantId, 'first_real_driver')`

**The drivers route (`/api/v1/carrier/fleet/drivers/route.ts`) has no `recordActivationEvent` call and should not get one.** The invitation acceptance is the correct trigger point — it fires when a real human has actually created an account (not just when the owner creates a carrier_driver record without an associated login).

**No dispatch-side driver trigger is needed for Plan 50-05.**
