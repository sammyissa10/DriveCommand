**The public tracking feature is not live.** Nobody holds a token, because no row carries one.

## The decision — (b), and it contradicts a literal reading of the plan

The plan makes "(c) leave it and report" *"correct only if the production count is 0"*, and the count
is 0. **(b) was taken anyway**, and the argument is the measurement below rather than a preference.

`08-track-probe-before.json` — one disposable legacy `Load` with a token seeded on staging (plus the
disposable `Customer` its NOT NULL `customerId` requires), driven **with no session at all**:

```
seeded: true
HTTP 500  TC001 in window: 2
VERDICT: FAILS — the page raises as app_user the first time a token exists
```

So "not live" and "harmless" are different claims, and only the first is true. The page is a landmine
sitting directly on the cutover path: the very first customer-facing tracking link would have
produced a 500 on a public page.

### Why it cannot be tenant-scoped, and why not a `SECURITY DEFINER` resolver

The caller is an anonymous member of the public. There is **no session and therefore no tenant until
the token resolves one** — the token IS the capability. `getTenantPrisma()` would have to throw
before the lookup that tells it which tenant to be. The tripwire could never have passed here; what
it actually offered was a guaranteed raise, which is what the 500 above is.

Option (a), a narrow `SECURITY DEFINER` resolver, is the more principled shape and was rejected: it
is DDL, therefore a migration, therefore drift this task would own — and it would create a **second
mechanism** for a lookup that already has an approved, reviewed one three files away.

### Why (b) is not a new decision

`src/app/api/track/[token]/route.ts:26` already does
`getAdminDb('public shipment tracking lookup')` for the **byte-identical** query shape, and
`app_admin` already holds SELECT on exactly the four tables that path needs — verified against
`information_schema.role_table_grants` on BOTH databases rather than taken from the migration name:

```
PROD  GPSLocation:SELECT | Load:SELECT | Truck:SELECT | User:SELECT
STG   GPSLocation:SELECT | Load:SELECT | Truck:SELECT | User:SELECT
```

`Truck` and `User` matter: the page `include`s `truck` and `driver`, so a check of `Load` and
`GPSLocation` alone would have been the same incomplete reading that produced Task 5's two surprise
`42501`s. **No new `AdminReason`** — the existing string is exactly this path. **No DDL.**

Both of the page's reads moved. Leaving the `gPSLocation.findFirst` on the bare client would have
left the page raising on any load with a truck assigned, which is every load worth tracking.

### The cost, stated rather than buried

`app_admin` bypasses RLS, so `unmigrated-path-tripwire.md` §8 item 2 applies: this path is now
outside the tripwire's reach. It needed an `ADMIN_ALLOWLIST` entry, and the gate refused it first:

```
 FAIL  tests/security/admin-connection-allowlist.test.ts > … > allowlist equality, BOTH directions
AssertionError: these files import lib/db/admin-prisma but are NOT in ADMIN_ALLOWLIST:
  app/track/[token]/page.tsx: expected [ 'app/track/[token]/page.tsx' ] to deeply equal []
```

Entry added with a call count and a `minBytes` floor; integrity floor 22 → 23 files, 43 → 44 calls.

## 6b — `carrier-auto-dispatch`: the fixture, and the product defect under it

Staging's two `route_templates` rows, read rather than assumed:

```
Alpha Daily Lane  schedule_type=on_call  recurrence_rule=NULL  auto_generate_days_ahead=7  active=true
Beta Daily Lane   schedule_type=on_call  recurrence_rule=NULL  auto_generate_days_ahead=7  active=true
```

`autoGenerateDaysAhead` **defaults to 7** (`schema.prisma:2297`, and `column_default = '7'` on
staging), so a template created without naming it is auto-generating. `generateDispatches` throws
`Template has no recurrenceRule — nothing to generate` on precisely that combination.

Corrected **reproducibly in `scripts/seed-staging.ts`** — `autoGenerateDaysAhead: 0` — and the same
correction applied to the two live staging rows (2 rows updated, read back).

**Why 0 and not a recurrence rule.** An on-call template that does not auto-generate is a coherent
fixture. A template carrying a rule would still fail one step deeper:
`dispatch-generator.ts:335` dereferences `template.defaultDriverId!` and `template.defaultTruckId!`,
and **both are NULL on both seeded templates** (read, not guessed). Exercising the generation path
needs three more fixture fields *and* a cleanup path for the trips, loads and stops it writes. Named
in §8 of the report rather than smuggled in here.

### After

Row 3 answers **HTTP 200** with zero `TC001`. The harness calls it **`LATENT`**, correctly: its data
gate — `route_templates` with `autoGenerateDaysAhead > 0` — now reads 0, so the route completed
having found nothing to do. **quick-604 §8 item 10's gap is NOT closed**: the route's tenant-scoped
generation work is still unmeasured, and now for a stated reason rather than an accident.

### Reported, not fixed — the product defect

The product permits a `route_template` with `autoGenerateDaysAhead > 0`, `scheduleType: 'on_call'`
and **no** `recurrenceRule` (quick-521 lowered that floor to 0), and the nightly cron 500s on it —
which, before quick-603, it did silently. That is a real defect with a real owner and it is not this
task's. Two fixture rows were the only reason it was visible here; a tenant that saves such a
template in the UI gets the same nightly failure.
