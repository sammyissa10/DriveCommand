<objective>
Lower the `autoGenerateDaysAhead` validation floor from 1 to 0 in the three places it is
enforced, so that the three production `on_call` route templates — which correctly store
`auto_generate_days_ahead = 0` — can be edited and saved again.

Purpose: every `on_call` template is currently uneditable. The desktop form's `min={1}`
makes the browser refuse to submit at all (tooltip "Value must be greater than or equal
to 1.", zero network requests), so an unrelated change such as an End Stop policy
selection cannot be saved. `0` is the semantically correct value for a template with no
recurrence rule and no scheduled departure — the auto-dispatch cron already filters
`autoGenerateDaysAhead: { gt: 0 }`, i.e. 0 already means "do not auto-generate" to the
only consumer.

Output: 3 single-token edits (`1` → `0`), a probed `tsc --noEmit` gate, and a written
report of one out-of-scope inconsistency found during investigation.
</objective>

<report_only>
**Do NOT implement this — record it in the SUMMARY as a finding.**

The desktop **Auto Generate Days Ahead** field at `RouteTemplateForm.tsx:787-806` is
rendered **unconditionally** — it is not gated on `scheduleType`. Both mobile variants
(`TemplateEditMobile.tsx:307`, `NewTemplateMobile.tsx:243`) gate the equivalent row behind
the recurrence-fields conditional, so the field is already hidden for `on_call` there.

That desktop/mobile inconsistency is the deeper reason the bug was reachable at all: on
desktop an `on_call` template shows — and validates — a field that has no meaning for it.
Hiding it on desktop for `on_call` is the obvious follow-up, but it is a behaviour change
to a form shared by all schedule types and is explicitly out of scope here. Report it;
do not gate the field in this task.
