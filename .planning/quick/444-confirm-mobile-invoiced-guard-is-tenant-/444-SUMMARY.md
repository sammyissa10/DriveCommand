# Quick Task 444 — Summary
## Confirm mobile INVOICED guard is tenant-safe under bypass_rls

**Verdict: SAFE — tenant isolation is preserved.**

---

## Q1: Is the load pre-validated as the caller's tenant before the guard runs?

**YES.**

`apps/web/src/app/api/mobile/owner/loads/[id]/route.ts`, lines 176–199:

```typescript
existingLoad = await prisma.$transaction(async (tx) => {
  await tx.$executeRaw`SELECT set_config('app.bypass_rls', 'on', TRUE)`;
  return tx.load.findUnique({
    where: { id, tenantId },   // ← tenantId from verified JWT
    select: { id: true, ... },
  });
}, TX_OPTIONS);

if (!existingLoad) {
  return NextResponse.json({ error: 'Load not found' }, { status: 404 });
}
```

The handler returns **404 before reaching the invoice guard** if `id` does not match the caller's `tenantId`. `tenantId` is extracted from the AES-256-GCM Bearer token by `validateMobileToken()` (line 127) — it is not user-supplied.

## Q2: Is `Invoice.loadId` a FK to a globally-unique Load PK?

**YES.**

`apps/web/prisma/schema.prisma`:

- **Line 1223:** `Load.id String @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid` — globally unique UUID, not tenant-scoped
- **Line 1049:** `Invoice.loadId String? @db.Uuid`
- **Line 1075:** `load Load? @relation(fields: [loadId], references: [id])` — FK to `Load.id`

A UUID generated by `gen_random_uuid()` is globally unique. A given `loadId` value belongs to exactly one `Load` row, which in turn belongs to exactly one tenant via `Load.tenantId`.

## Q3: Is the bypass_rls invoice.count safe?

**YES.**

Lines 205–210:
```typescript
invoiceCount = await prisma.$transaction(async (tx) => {
  await tx.$executeRaw`SELECT set_config('app.bypass_rls', 'on', TRUE)`;
  return tx.invoice.count({
    where: { loadId: id, status: { not: 'CANCELLED' } },
  });
}, TX_OPTIONS);
```

Isolation is preserved by two independent guarantees:

1. **Pre-validation:** By line 197, `id` has already been confirmed (via `findUnique({ where: { id, tenantId } })`) to belong to the authenticated tenant. If it did not, the handler returned 404 and never reached this code.

2. **Globally-unique FK:** `Load.id` is a UUID PK. No two loads share the same `id` across any tenant. Therefore `invoice.count({ where: { loadId: id } })` cannot inadvertently match invoices from another tenant — the `loadId` is exclusive to one tenant's load.

Counting invoices by `loadId` under bypass_rls is equivalent to counting them under RLS for this specific case, because the scoping invariant is enforced upstream.

## Q4: Is there ANY path where `id` reaches the guard without pre-validation?

**NO.**

Execution order is strictly linear:

| Step | Line(s) | Action |
|------|---------|--------|
| 1 | 127–132 | `validateMobileToken` — verifies Bearer, extracts `tenantId`/`userId`/`role`. Unauthorized → 401 |
| 2 | 130–132 | Role check — non-OWNER → 403 |
| 3 | 133–135 | Rate limit |
| 4 | 176–191 | `findUnique({ where: { id, tenantId } })` — tenant-scoped load lookup |
| 5 | 197–199 | 404 if load not found |
| 6 | 202–221 | **INVOICED guard** — only reachable if step 4 passed |

There is no code path that skips step 4 and reaches step 6. No early-return path, no conditional bypass.

## Conclusion

The `invoice.count` under `bypass_rls` in QT-443 is **tenant-safe**. The bypass_rls flag does not create a cross-tenant data leak here because:

- `id` is already proven to belong to the caller's tenant before the guard executes (step 4/5 above)
- `Load.id` is a globally-unique UUID PK; a foreign-keyed `loadId` cannot resolve to a different tenant's data

No fix required. The pattern mirrors how the final `tx.load.update({ where: { id } })` at line 275 is also safe (same pre-validation reasoning, with an inline comment confirming it).
